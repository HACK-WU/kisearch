## 1. 目标

让 daemon 具备「**检索问答 + 流式生成 + 会话落盘**」的完整后端能力：用户提问后，模型能自主调用 `kb_search` 检索当前 scope 知识库，基于检索结果流式作答，并给出可核对的来源引用。

## 2. 场景

1. **文本问答带检索**：用户问「ki_search 的 fulltext 模式有什么特点」→ 模型调用 `kb_search` 检索 → 基于命中片段作答 → 回答附来源引用（group / 文档 / 行号），落盘可在刷新后复原
2. **检索无命中**：问一个知识库里没有的事 → 必须如实回答「知识库中未找到相关内容」，**不得用模型自身知识冒充**
3. **模型不支持工具调用**：`supportsTools=false` → 走预检索降级（daemon 代跑一次检索）+ 发 `degraded` 事件明示
4. **重新生成 / 编辑重发**：重生成不新增 user 消息；编辑 user 消息后原子截断其后消息

## 5. 划分理由（写进包，不留在对话里）

| 项 | 内容 |
|----|------|
| **为什么这样切** | 后端是一条**逐层依赖的串行链**（`llm-client` → `retrieval` → `chat-store` → `chat-routes`），**内部无法并行**，故整体作为一片 |
| **为什么与 SR-02 可分** | 前后端目录**天然互斥**（`src/lib/**` ∩ `web/src/**` = ∅），且靠 **SSE 事件协议**（已冻结的形状）解耦——SR-02 用 mock 即可独立开工 |
| **与谁不可并行及原因** | 后端 4 个模块之间**共享同一个执行上下文**（工具循环要同时驱动 llm-client 与 chat-store），强行拆分会让两片都必须改 `tool-loop.ts` → **互斥不成立** |
| **否决过的划分方式** | ① **按 4 个模块拆 4 片** → 否决：每片都依赖上一层实现（非仅接口），同批无法开工；② **把 `chat-store` 单独成片** → 否决：它与 `tool-loop` 的落盘时序强耦合（两段加锁语义），拆开必然冲突；③ **把 mock 生成纳入本片** → 否决：mock 属脚手架，由切片阶段统一产出（两片共用） |

## 6. 计划内的阻塞点（预期会卡住、需提前知道的）

| 阻塞点 | 处理 |
|--------|------|
| **daemon 框架层未验证**（鉴权 / 配置快照 / 白名单 / 长连接关闭语义） | 前置门① 只验了长流与工具往返（独立进程）。**本片第一步**：在真实 daemon 上跑通一条最小 `/api/chat/*` 请求 + 一次生成，确认框架层后再往下做 |
| `tool_calls` 累积拼接 | 契约里已警示的**标准陷阱**：必须按 `index` 累积（首块给 id/name，后续给 arguments 片段）。参考实现在 `.delivery/verify-gate.mjs` |
| 强制作答方式 | **拿掉 `tools` 再调一次**（不是截断——截断会得空终答）。见 `design/gate1-verification.md` §2.3 |
| 每个 `tool_call` 必须回一条 `tool` 消息 | 实测首轮可能返回 2 个 tool_calls，漏一个 → 模型反复请求（循环不收敛） |
