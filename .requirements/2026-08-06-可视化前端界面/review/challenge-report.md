# 🎯 设计文档质疑报告（challenger）

> 质疑对象：`design/DESIGN.md` + S01~S05 子文档
> 质疑时间：2026-08-08
> 前置：design-review 已通过（评审修复 10 项）

## 📋 设计上下文确认

- **设计目标**：为 ki 构建可视化 Web 前端（5 页面），复用 `ki mcp --http` + 方案 A 扩展
- **范围**：`--web` 静态服务、`/api/*` 路由、前端工程、zvec 占位
- **约束**：前端不启动服务、scope 必选、批量写入取消、破坏性操作留 CLI
- **隐含假设**：①`--web` 同源规避 CORS（已实证 SDK Client 模块 0 处 `process.` 引用 ✅）②导入在 HTTP 内复用锁/信号

## ⚔️ 反对意见

### 意见1：`/api/*` 与 SPA fallback 的路由优先级（🟡，已修复）
- **反对理由**：S-01 已修复"`/api/*` 优先于静态服务"，但父文档 §4 风险表仍写"其余 → 静态"
- **功能影响**：预期 404 返回 JSON → 实际若按"静态优先"实现，前端 JSON.parse 到 HTML 崩溃
- **处置**：✅ 已修复（父文档 §4 同步"/api/* 未匹配返回 JSON 404 不 fallback"）

### 意见2：`handleDirectImport` 的 `process.exit(130)` 杀服务进程（🟡，已确认语义）
- **反对理由**：`onInterrupt`（import.ts:233-242）捕获 SIGINT/SIGTERM → `process.exit(130)`，HTTP 多会话共享进程会整体退出
- **功能影响**：预期仅终止导入 → 实际服务整体退出、所有会话中断
- **处置**：✅ 已确认（S-03 记录：`ki mcp --http --web` 是前台 daemon，Ctrl+C 关服务属预期；导入中断标记/清锁在退出前同步执行，重启可恢复）。**待实现时确认 IDE 守护场景无 SIGTERM 误发**

### 意见3：base64 上传 16MB 实际 ~12MB 有效载荷（🟢，已明确）
- **反对理由**：base64 膨胀 33%，16MB 上限实际 ~12MB 文件内容
- **功能影响**：分批次数比预期多
- **处置**：✅ 已明确（S-03：前端分批基准按 base64 后大小计算，单文件 ≤1MB 不受影响）

### 意见4：`/api/doc/list` 无缓存 + 无防抖（🟡，已修复）
- **反对理由**：每次请求全量读 relations-cache JSON；浏览页高频文件名搜索
- **功能影响**：大 scope 浏览页卡顿
- **处置**：✅ 已修复（S-02 加 TTL+mtime/size 缓存；S-04 前端 300ms 防抖）

### 意见5：`/api/health` 高频轮询触发重探活（🟢，已明确）
- **反对理由**：总览页若自动轮询，每次触发完整 doctor（含 zvec 探活）
- **功能影响**：无（仅加载查一次 + 手动刷新）
- **处置**：✅ 已明确（S-04：仅加载时查一次 + 手动刷新按钮）

## ✅ 认可点

1. `--web` 同源规避 CORS 是方案 A 最大红利，SDK 浏览器兼容性已源码实证
2. 导入复用 `handleDirectImport` 纯函数（自带锁 + 中断标记），避免重复实现
3. `/api/doc/list` 返回 Group 路径 + 文档（v4 契约），浏览/搜索数据源清晰分离
4. 异步 job 模型 + status 轮询，避免导入挂起 HTTP

## ➕ 补充场景与情况

1. `--web` 目录不存在（`web/dist` 未构建）：静态服务应返回友好提示而非 500
2. 大文件上传（>1MB）：前端需校验提示（S-03 已限 1MB）
3. MCP SDK 浏览器 bundle：Vite 打包需验证 `eventsource-parser/stream` 的 ESM 解析
