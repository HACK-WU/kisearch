## ⚔️ 反对意见

### 意见1：`buildMemoryIdMap` 多值映射的构建时机与一致性存在未设计盲区
- **反对理由**：设计文档 §3.2.1 说"构建时遍历 relations-cache 按前缀聚合"，但未说明**何时构建**（每次增量调用时全量重建？缓存失效策略？）。relations-cache 会被 sync-relation（写入）、delete-relation（删除）、boundaryDecay（衰减移除）多个路径修改——若增量构建时机未与这些写入点对齐，diff 定位会拿到过期/不全的 memoryId 列表，导致 deleted 清理漏删、modified 覆盖不净。
- **功能影响**：预期"文件删除后该文件全部 chunk 清理干净" → 实际若 Map 基于过期 cache 构建，可能漏删部分 chunk 向量，形成悬空向量/孤儿数据（检索到但无 KB 对应）。
- **严重程度**：🔴 致命（数据一致性 + 构建时机未设计）
- **替代方案**：明确构建时机——①每次增量调用时从当前 relations-cache 现场重建（最简单，低频场景可接受）；②复用现有 `relation-map` 的 TTL + mtime/size 双失效缓存机制（一致性更强）。建议明确选型并说明失效触发点。
- **验证方法**：构造"先 sync-relation 写、再删除文件跑增量"序列，检查 deleted 是否清理该文件全部 chunk。

### 意见2：增量 modified 的"删旧全 chunk"与"写新全 chunk"顺序原子性未设计
- **反对理由**：H-17 说 modified = 删旧全 chunk + 写新全 chunk。但设计未说明顺序与失败语义：先删后写，若写入中途失败 → 文件数据丢失（旧 chunk 没了新 chunk 没写全）；先写后删，若删除失败 → 新旧并存（重复）。现有增量有"全部成功才更新 source.commit"的兜底，但 chunk 覆盖的中间态未设计。
- **功能影响**：预期"modified 后文件新内容完整可检索" → 实际若写入中断，用户检索到的是不完整/部分缺失的文件内容。
- **严重程度**：🟡 重要（有 commit 兜底但中间态脏数据可检索）
- **替代方案**：明确写序——先写新全 chunk，全部成功后再删旧 chunk（新数据先就位，旧数据后清理）；删除失败时保留旧 chunk（下次增量重试清理），配合"全部成功才更新 commit"形成幂等重跑闭环。
- **验证方法**：模拟写入中途失败（kill 进程），检查修改后文件检索是否完整、重跑增量能否自愈。

### 意见3：切分参数持久化到 source 块的首次/后续变更语义未设计
- **反对理由**：H-18 说"`--chunk-size/--chunk-overlap` 记录到 source 块，增量自动复用"。但未设计：①用户后续修改 chunk-size 再全量重导时，旧 chunk 划分与 source 块新参数不匹配——是否需要"重切全库"或"仅新文件生效"？②增量时 source 块有 chunkSize 但命令行又传了新值——以哪个为准？
- **功能影响**：预期"切分参数跨次一致" → 实际若参数变更语义模糊，可能出现同一文件新旧 chunk 划分不一致，增量 modified 时按新参数重切，但删旧 chunk 用的是旧划分——漏删/残留。
- **严重程度**：🟡 重要
- **替代方案**：明确参数变更语义——source 块持久化参数为唯一权威；命令行传参仅首次导入（或显式 `--force-rechunk`）时生效；参数变更时对受影响文件整体重切（文件级全量覆盖，天然兼容）。
- **验证方法**：先 1000 字符导入，改 500 再增量，检查 modified 文件 chunk 是否完整重建无残留。

### 意见4：进度文件（断点续跑）与 chunk 粒度的幂等冲突
- **反对理由**：P-3 定方向 progress entry 三字段 `{sourcePath, file, index}`。但 full 模式断点续跑语义是"跳过已完成条目"——若一个文件切了 10 个 chunk，其中 5 个已写入后中断，续跑时按 sourcePath（chunk 级）跳过已完成的 5 个。但向量写入是幂等 upsert（doc id 确定性），而 relations-cache / local KB 写入是否幂等？若 writeRelations 按文件级原子写（整个文件 10 个 chunk 一起写），中途中断会留下"只写了 5 个 chunk 的 cache 条目"，续跑跳过 5 个已完成的 chunk 但 cache 不完整——数据不一致。
- **功能影响**：预期"断点续跑后数据完整" → 实际可能出现 relations-cache 只含部分 chunk，检索漏召回。
- **严重程度**：🟡 重要
- **替代方案**：进度跳过的最小粒度定为文件级（一个文件要么全部完成要么重来），chunk 级 index 仅用于进度展示；或 writeRelations 按 chunk 级独立原子写。
- **验证方法**：构造 10-chunk 文件，写入 5 个 chunk 后中断，续跑验证 cache 是否完整。

### 意见5：删除 `scan` 子命令后，`scan-index.json` / `getScanIndexPath` 的消费方未清点
- **反对理由**：REQ-04 说删 `scan` 子命令，但 `getScanIndexPath` 可能仍被其他模块（如增量 diff 的基线？或旧数据读取）引用。设计文档只列"删除实体"没做消费方清点——若某处仍读 scan-index.json，删除后该处读 null，可能静默降级或报错。
- **功能影响**：预期"干净删除" → 实际若遗漏消费方，可能出现运行时读取 null / 残留代码。
- **严重程度**：🟡 重要（属于删除链路完整性）
- **替代方案**：技术设计阶段用 grep 清点 `getScanIndexPath` / `scan-index.json` 全部引用点，逐点确认删除或改为 null 安全。
- **验证方法**：`grep -rn "scan-index\|getScanIndexPath" src/` 全量清点。

### 意见6：全文直导后 BM25 全文检索的词项爆炸
- **反对理由**：删除 keywords 后，向量 content = chunk 原文（可能 1000 字符 × 数千文件），BM25（jieba 分词）索引规模从"AI 摘要+关键词"变为"全量原文"。zvec 的 FTS 索引对全文的索引构建时间 / 存储膨胀 / 检索延迟未评估。设计文档 §4 只说"复用批量向量化"未提 FTS 规模影响。
- **功能影响**：预期"直导后检索快速" → 实际大规模全量直导可能索引构建慢 / 检索退化。
- **严重程度**：🟡 重要（性能风险未评估）
- **替代方案**：技术设计阶段补充 FTS 索引规模的量化评估（chunk 上限 1000 字符对 FTS 是可接受量级？实测基准）；必要时调整 chunk-size 默认值。
- **验证方法**：1000 文件全量直导，测量索引构建时间与 search 延迟。

## ✅ 认可点

1. **方案②选型正确**：`buildMemoryIdMap` 多值映射复用 relations-cache，不新增数据文件，符合"删除实体最小化"原则——比方案①（独立索引）更优。
2. **直导不触发 Wiki 写回**的决策精准——避免了 chunk 的 `{relation}.md` 污染外部源目录，是评审后修复的高质量决策。
3. **文件级全量覆盖更新（H-17）**大幅简化了增量复杂度——不做 chunk 级 diff 精确定位，幂等可重跑，工程上务实。
4. **local KB 按 chunk relation 粒度存储**与 relation 命名（`文件名-N`）自洽，检索→反查→定位链路闭环。

## ➕ 补充场景与情况

1. **同文件多 scope**：同一 wiki 目录导入多个 scope，chunk 划分在 scope 间重复计算（幂等性 OK，但重复切分浪费）——可接受，标注。
2. **文件重命名**：git diff 的 rename（R 状态）——现有 `parseGitDiff` 将 R 拆解为 deleted+added，文件重命名后新文件重新切分、旧文件 chunk 清理，链路正确但会全量重建，标注性能影响。
3. **chunk 边界跨 markdown 代码块**：固定长度切分可能把代码块劈开（`\n\n` 在代码块内存在时）——递归切分的分隔符优先级无法感知 markdown 结构，可能切在代码块中间，语义受损但可接受（H-07 已确认固定长度方案）。
4. **增量无进度文件的失败恢复**：增量中断后重跑是幂等的（文件级覆盖 + commit 兜底），但重跑会重复 diff 计算——大 scope 下 diff 开销重复，可接受（低频）。
5. **超长单文件（>10MB）**：现有 scan 有 `MAX_SCAN_FILE_SIZE` 限制——直导是否保留该上限？超大文件切分会产生大量 chunk（如 10MB/1000字符 ≈ 10000 chunk），单文件向量数爆炸需评估上限。
