# 多库检索的执行流程

> 本文讲一次多库检索（知识视图 / `--scope a,b`）**实际做了哪些事、每步取多少条**。
> 分数的计算公式见 [多库联合查询的排序规则](./multi-scope-ranking.md)；单库查询不受本文影响。

---

## 一、总览

以**返回 20 条**（`limit=20`）、视图有 **14 个库**为例：

```text
每个库：
  ① 向量查询 top-40        ┐
  ② 全文查询 top-40        ┘→ 按文档 id 对齐，每条挂上「向量分 + 字面分」
                              ↓
  ③ 逐条算最终分 = (名次分 + 字面分 / 10^(d+1)) / 2
                              ↓
  ④ 库内按最终分排序 → 取 top-20（每库配额）
                              ↓
14 个库 × 20 = 280 条 → 全局按最终分排序 → 取 20 条返回
```

三个容易误解的点：

- **不是「先把 14 个库的结果混在一起排序」**，而是每个库先在内部算分、选出自己的 20 条代表；
- **不是「两个结果列表求并集再去重」**，而是按文档对齐 —— 同一条文档的两路分数都要留下；
- **每库取 40、只留 20**：40 是用来算分的原料，20 才是参与全局排名的配额。

---

## 二、哪些库参与本次检索

| 库的状态 | 处理 |
|---|---|
| 有向量索引 | 正常参与（向量 + 全文两路） |
| **没有向量索引** | 跳过，并在结果里列出「该库没有向量索引，未参与本次语义检索」 |
| 本次查询的向量计算失败 | 所有库改走字面匹配，见第五节 |

> **为什么不给「没有向量索引的库」做补偿**：语义检索的结果应当来自具备语义能力的库。
> 把一个只能做字面匹配的库混进来，它的「名次分」是凭空造出来的，排序会失真。
> 想检索这类库，用全文模式或单独指定它即可。

---

## 三、每个库取多少候选

以返回 20 条为例：

| 步骤 | 条数 |
|---|---|
| 向量查询 | 前 **40** 条 |
| 全文查询 | 前 **40** 条 |
| 对齐后候选 | 最多 **80** 条（两路完全不重叠的极端情况） |
| 库内排序后保留 | 前 **20** 条 |

> 每路的取数有个**下限 40 条**：即使本次只返回 5 条，两路也各取 40 条来算分。
> 否则候选太少，「只在字面路排第一」的文档很容易被漏在外面。

### 两路结果是按文档对齐的，不是「合并两个列表」

向量查询和全文查询是两个**不同的查询**，各自返回一批文档。理想情况下两路返回的是同一批文档，只是分数不同：

```text
向量查询 top-40  →  [{文档A, 0.63}, {文档B, 0.72}, ...]
全文查询 top-40  →  [{文档A, 90.9}, {文档B, 1.09}, ...]
                        ↓  按文档 id 对齐（不是求并集再删重复）
每条候选拿到自己的两个分数：
  文档A: 向量 0.63 + 字面 90.9
  文档B: 向量 0.72 + 字面 1.09
```

**同一条文档的两路分数都要留下**，不是「去重留一份」。

两种边界：

| 情况 | 结果 |
|---|---|
| 两路 top-40 **完全重合**（理想状态） | 40 条候选，每条两个分数 |
| 两路**完全不重合**（极端情况） | 80 条候选，每条只有一个分数，另一路记 0 |

实际通常是中间态 —— 同一次查询里两路都能召回的文档往往只有个位数，所以候选数接近 80。

### 三个「为什么」

**为什么两路要各取 2 倍（20 → 40）**：两路召回的文档往往不是同一批，各取 20 条时对齐后可能只剩十几条 —— 字面分最高的文档会漏在外面。取 2 倍是为了让「只在全文路排第一、向量路完全没召回」的文档也能进来参与算分。

**为什么必须「库内先算分」**：如果先把各库结果按名次混在一起、之后再算分，那么「字面分极高但名次一般」的文档会在混合阶段就被名次更整齐的文档挤掉，公式根本没机会看到它。先算分、再排序，它才能凭字面分在库内排到前面。

**每库为什么只留 20 条**：留得太多会让候选数量爆炸（14 个库就是几百条），留得太少又可能把真正相关的挤掉。以返回条数作为每库配额，既保证每个库都有公平机会，又不会让某个大库吃满全部名额。

> 库里文档不足配额时，按实际数量取，不补空位。

---

## 四、合并与截断

各库的 N 条候选汇总后，按得分统一排序，取前 N 条返回。

- 因为每库的得分已经用同一个公式算过，**跨库之间可比**，合并时不需要再做换算；
- 每个库最多贡献 N 条，所以单个库不会占满全部名额；
- 响应里的 `matchedByScope` 会说明本次结果来自哪些库、各多少条。

---

## 五、超时与降级

### 降级：向量计算失败时

如果本次查询的向量计算失败（例如 embedding 服务不可用或超时），所有库都会改走字面匹配。此时**不再套用加权公式** —— 两路已经合并成一路，再加权等于同一份分数算两遍。

界面与响应会标注「已降级为全文检索」，排序直接按字面分。

### 超时：分三层

| 层级 | 规则 |
|---|---|
| 查询向量计算 | 失败即**全局降级**（见上）—— 查询向量只有一份，无法按库分别降级 |
| 单个库 | **5 秒**内没返回，跳过该库并上报原因，其余库照常出结果 |
| 整次检索 | **8 秒**总预算，仍未完成的库记为「未在预算内完成」 |
| 全部库都失败 | 明确报错，**不返回空结果冒充**「没有命中」 |

> 为什么不「把所有超时都调大」：库是并发查的，调大只会让最慢的那个库拖住整次响应。给总预算更划算 —— 用户总能在固定时间内拿到「部分结果 + 明确缺了谁」。

## 六、单库查询为什么不一样

单库请求（`--scope <一个库>`）**不走上面这套流程**：

| | 单库 | 多库 |
|---|---|---|
| 候选放大 | 不放大，按 limit 取 | 每路取 2 倍 |
| 库内配额 | 无（就一个库） | 每库 N 条 |
| 排序依据 | 引擎自身的融合分 | 公式重算后的得分 |
| 分数量级 | `0.0x`（名次分） | 见 [排序规则](./multi-scope-ranking.md) |

所以**同一个查询、同一篇文档，单库和多库看到的分数和名次可能不同** —— 这不是异常，两者用的是不同的排序方式。
