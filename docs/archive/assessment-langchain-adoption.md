# 评估：是否引入 LangChain（TS 版）替换自研对话实现

> 问题：**为什么不用 LangChain？很多都是封装好的，直接用不是更好、更稳定、更利于后续扩展？**
> 取证：本仓实现实测（103 条单测 + 13 步真实链路 e2e）+ 你已完成课程的两份沉淀
> （`Desktop/learning/langchain/langchain/08-实战经验.md` 十故障模式、`09-排障速查手册.md` 十一症状）
> 日期：2026-09-29　｜　结论归属：**建议不做整体替换**，按「能力是否通用」分层引入（详见 §5）

---

## 1. 结论先行

| 判断 | 回答 |
|------|------|
| 用框架**更稳定**吗？ | **不会自动更稳定。** 它把一批常见坑变成"默认行为"，但同时引入**另一批新故障面**（中间件判重、检查点缺失、限额默认值 9999、序列化 CVE、错误码在本版本才落地）——你手册里 11 条症状有 9 条是框架**自身**的故障模式 |
| 用框架**更好扩展**吗？ | **在"能力扩张"维度上是。** 多供应商、多 agent、HITL 审批、记忆策略、Evals/追踪——这些框架确实替你封装了 |
| 本项目**现在该换**吗？ | **不建议整体替换。** 核心链路已被**冻结契约 + 前端副本 + 契约对齐测试**锚定，向量层是自研 zvec（框架抽象覆盖不到），换框架 = 重写核心链路 + 改契约 + 重写测试 |
| 本项目**最该补**的是什么？ | 不是框架，是**观测与评估**（你的落地 Checklist 里本项目唯一整块缺失项） |
| 中期怎么走？ | 新能力（多 agent / HITL / 结构化输出 / 评估）**用框架起步**；与冻结契约耦合的部分**继续自研** |

## 3. "更稳定吗？"——用你的两份沉淀做证据

### 3.1 框架把哪些坑变成"默认行为"（这是真收益）

| 你的故障模式 / 症状 | 框架提供的能力 | 若本项目自研需自己做 |
|---|---|---|
| 故障模式 1：工具异常**打停 agent**（异常冒泡） | `handle_errors` / `wrap_tool_call` 转 ToolMessage | 每个工具的"失败契约"自己定（本项目已有：`tool_end.error` 字段 + 不注错降级） |
| 故障模式 2：**循环/成本失控**（默认 `recursion_limit=9999`） | `ModelCallLimit` / `ToolCallLimit` 中间件 | 自己配轮次上限（本项目已有：`maxToolRounds=3` + `tool-rounds-exhausted` 事件） |
| 故障模式 3：长会话越聊越贵（全量 vs 摘要实测 135 vs 303 token） | 短期记忆（裁剪/摘要）中间件 | 自己做消息裁剪策略（本项目目前**全量历史**，未做摘要——见 §6 待办） |
| 故障模式 6：**没挂 checkpointer → 中断恢复 RuntimeError** | 检查点（测试 InMemorySaver） | 自己会话落盘（本项目已有，且已绑列表/归档/删除 API） |
| 故障模式 8：测试假信号（fake 模型的 `bind_tools` 未实现 / cassette 失配被包成 Connection error） | 官方 fake + 录制回放工具链 | 本项目做法：**mock 上游 http 服务捕真实请求体**（今天刚用它抓出"本轮 user 重复两次"） |
| 故障模式 9：结构化输出"文档能跑我不能跑"（thinking 模式拒绝强制定向、`ToolStrategy` 声明时机） | `response_format` + schema | 本项目当前无结构化输出需求 |
| 故障模式 10：多智能体/有状态迁移陷阱（无检查点则技能复用不生效、state 默认值不写入） | LangGraph + 显式 state | 未涉及多 agent |

**小结**：框架最大的价值是**把"上线前必须做对的事"变成有默认实现的构件**——但注意这些默认值不都安全（`recursion_limit=9999` 就是反例），你的"落地 Checklist 14 项"该配的还是得配。

### 3.2 框架引入的**新**故障面（这是真代价）

| 证据（你的沉淀） | 性质 |
|---|---|
| 症状 6：`similarity_score_threshold` 在内存向量库直接 `NotImplementedError` —— **接口承诺 ≠ 实现可用** | **抽象层与实现层不齐**。引入后你能拿到"统一接口"，但接口背后的实现可能没落地 |
| 症状 7：中间件默认按 name 判重 → 启动即 `AssertionError` | 组装期新失败点 |
| 症状 5：结构化输出被服务端拒绝（与思考模式耦合） | 框架能力与上游模型能力**耦合**，本项目用的正是**推理模型**（返回 `reasoning_content`） |
| 症状 11：tracing 无 key 时静默降级 + 后台 401；环境变量在**首次调用时固化** | 观测层也会"静默失败" |
| 案例 3：`langchain-core` CVE-2025-68664（序列化注入可泄密钥）、CVE-2026-34070（`load_prompt` 路径穿越） | **依赖安全面**：本项目现在 6 个运行时依赖；引入后攻击面变成几十个包，且要长期跟安全公告 |
| 附录 A 备注：7 条官方错误码中 **4 条文档标注 "Currently only used in langchainjs"** | 文档/实现**版本不对称**——TS 侧反而更完整，但也说明"文档写的 ≠ 你装的那版有的" |

### 3.3 自研同样要自己兜"标准陷阱"（本项目的实证）

今天这次实测正好是反例的镜像：

- 自研 `tool-loop.ts` 里 **"本轮 user 消息被重复拼进上游"** 存活了很久，**96 条断言全绿也抓不到**——因为现有测试都用手工构造的 conv，绕开了路由的写入时序。
- 也就是说：**不用框架 ≠ 自动正确**；框架替你把"通用陷阱"处理掉的同时，本项目自研面存在的风险要靠**自己的测试面**兜。本次的修法是补一类全新观测点（mock 上游捕真实请求体）。

> 结论：稳定性的来源是**测试与观测覆盖**，不是"用不用框架"。框架能提高**起点**，不能替代**验证**。

## 4. "更好扩展吗？"——按扩展方向逐项判

| 后续可能要做的功能 | 框架助力 | 本项目现状 | 建议 |
|---|---|---|---|
| 换/增模型供应商（多 provider） | 🟢 强（统一 `ChatModel`） | 只走 OpenAI 兼容协议，自研 40 行 SSE | 若真要多供应商 → 考虑引入 `@langchain/openai` 一类**薄封装**，不必上全套 |
| 多智能体 / 子 agent | 🟢 强（LangGraph + subagents） | 未涉及 | **新功能用框架起步**，别自研编排 |
| HITL 审批（危险动作人工确认） | 🟢 强（interrupt + checkpointer） | 未涉及 | 同上；但注意要先解决 checkpointer 前提（你的故障模式 6） |
| 记忆策略（裁剪/摘要/长期档案） | 🟢 强 | **全量历史，无摘要** | 先按你场景-01 的测算决定，再决定自研还是引入 |
| 结构化输出 | 🟡 中（受上游 thinking 模式限制） | 无需求 | 有需求时先按你故障模式 9 的路径验一遍 |
| 检索质量（切分/k/改写） | 🟡 中（Retriever 抽象 + 社区集成） | 自研 zvec + FTS 混合，**跨维度迁移/维度护栏是框架没有的能力** | 继续自研检索核心；框架只做上层编排 |
| 评估与观测（Evals / tracing） | 🟢 强且**本项目整块缺失** | 无 tracing、无 Evals | **最值得引入的一环**（见 §6） |
| 前端对话 UI（生成式 UI / 消息渲染 / 断流重连） | 🟢 强（AI Elements / assistant-ui / CopilotKit） | 自研 React 面板（按 demo 视觉基准） | UI 已成型且与自研契约绑定 → 不必换 |

## 5. 迁移成本量化（为什么"整体替换"不划算）

改动面 = 你项目里**已被锚定**的部分：

1. **契约重写**：`chat-contract.ts` 是**冻结 SSOT**（11 类事件 + 顺序约束 + `ChatConfigOk` + 错误码 + 预算常量），前端有同形状副本 `web/src/api/chatContract.ts`，一致性由 `contract-parity.test.ts` 机械保证 → 换框架事件形状 = 改契约 + 改前端副本 + 改 parity 测试 + 改 8 个 chat 测试文件。
2. **向量层要写 adapter**：框架 `VectorStore` 抽象不覆盖 zvec 的**跨维度迁移（确认门/中断回退/写入护栏）**与混合检索 → 仍需自研核心，只是多一层薄适配（新的维护面）。
3. **依赖面**：6 → 数十个运行时依赖，含 `langchain-core` 的 CVE 跟踪义务。
4. **已验证资产重测**：103 条单测 + 13 步 e2e + 权限 P1–P7 全部要按新链路重写。
5. **收益**：省掉的是"循环骨架 + SSE 解析 + 状态落盘"这三块的**自研代码量**，不是"能力"。

> 综合：**成本 ≈ 重写对话核心链路；收益 ≈ 少维护约千行自研代码**。在契约已冻结、测试已建成的前提下，这笔账不成立。

## 6. 建议路径（三档，不是全有全无）

### 立即可做（不引入框架，成本低、收益直接）

| 动作 | 依据 | 落地方式 |
|---|---|---|
| 补**检索质量基线**（问题集 + 期望命中块） | 你的故障模式 5 / 场景-03；本仓已两次踩"检索结果不可用却零报错" | 建 `tests/` 下的问题集 fixture + 命中断言 |
| 补**观测**（至少 request/conv 维度的结构化日志） | 你的故障模式 8/11；本仓已有 `chat-log.ts` 骨架 | 扩充 `chat-log.ts` 的事件与字段 |
| 上**上下文成本策略**（全量 → 裁剪/阈值摘要） | 你的故障模式 3（135 vs 303 token 实测）+ 场景-01 | 在 `buildUpstreamMessages` 前加裁剪策略 + 成本对照记录 |
| 把"**失败契约**"写成测试 | 你的故障模式 1 + 落地 Checklist | 工具失败返回形态已有（`tool_end.error`），补断言 |

### 中期（按需局部引入，不碰冻结契约）

1. **评估/追踪**：先接 tracing（注意"启动前配好、跑一次确认收到"），或自研等价物（本仓已有 `chat-log.ts`）。
2. **新的复杂编排**（多 agent / HITL）：**直接用 LangGraph 起新模块**，与现有 chat 链路并存，通过现有 SSE 契约对外输出（框架在内部，契约在边界）。
3. **多供应商**：若真需要，仅引入对应 provider 包做"薄适配"，替换 `llm-client` 内部实现，**对外事件契约不变**。

### 不建议

- 把现有 chat 核心链路（`llm-client` / `tool-loop` / `chat-store` / `chat-routes`）整体换成框架 —— 成本/风险显著高于收益，且冻结契约会被动晃。
- 为了"少写代码"引入全套框架 —— 你的 11 条症状说明：**框架多出来的抽象层，本身就是新的故障面**。

---

## 7. 一句话总结

**框架不是"更稳定"，而是"把通用工程做成默认值、把通用故障也一并打包"。**
本项目当前的瓶颈不在"缺框架"，而在**缺观测与评估**（你落地 Checklist 唯一整块空白项）；
最划算的走法是：**契约边界继续自研，通用能力（观测/评估/新编排）按需引入框架**。
