## 1. 执行摘要

1. **需求本质**：把「知识库交互」从**自研内置工具链**（`kb_search`）改为**复用既有 MCP 工具面**，并把「怎么用工具」从**硬编码常量**改为**可动态编辑的 skill + 触发提示词**。方向与项目既有架构同向——两条通路本来就共用同一个 `executeSearch` 引擎。`🟢`
2. **✅ P0 风险一：已由用户拍板接受，不再是阻塞项。** 事实：内置 `kb_search` 的工具 schema **刻意不暴露 `scope`**（N23 的结构性保证），而 MCP 的 `ki_search` **带 `scope` 参数**，且回环访问 `authScopes = null` → **免鉴权、不按授权过滤**（Web 前端正是回环）。
   **决策（2026-09-30 拍板）**：跨 scope 检索在本场景（**本地单用户工具**）**可接受**，不视为风险；`scope` **不由模型指定**，默认取**页面当前选中的 scope**。
   **实现约束不变**：仍须① schema 层剥离该参数 + ② 执行层白名单取键 —— 否则模型可能传值**覆盖页面值**。
   **唯一执行前提（新增 R11）**：切换页面 scope 时须同步切换会话，否则会出现"历史消息属 A、检索打到 B"的**上下文错配**（功能问题，非安全问题）。
3. **🔴 P0 风险二：12 个 MCP 工具里含写/删能力。** `store` / `bulk-store`（写向量）、`sync-relation` / `bulk-sync-relation` / `edit-relation`（写关系 + KB）、**`delete-relation`（删关系 + cache + KB + wiki + 向量）**、`manage-index`（Group 树 CRUD）。`🟢` 全量暴露 = 给 AI 知识库**写+删**权限。
4. **🟡 风险三：直接暴露 12 个工具，正命中你课程里的「场景-04 工具膨胀选错」**——工具从 6 涨到 30 会开始选错工具。当前是 1 个工具，暴露后是 12 个，且其中多个语义相近（`store` vs `bulk-store`、`sync-relation` vs `bulk-sync-relation`）。
5. **✅ 好消息：动态提示词后端已有一半基础，缺口只在前端入口。** `llm.defaultSystemPrompt`（config 字段）+ 会话级 `systemPrompt`（建会话可用、`PATCH /conversations/:id` 可改、有长度校验）都已实现 `🟢`；但 `web/src/` 全目录 **grep `systemPrompt` 零命中** `🟢` → 有后端无前端（典型 M3「结构可证」缺口）。
6. **⚠️ 会被扯断的一条现有能力：来源引用。** 现在 `sources`（group/doc/行号/snippet，前端"引用 N 处 + 点击回原文"）来自**投影层**对 `executeSearch` 结果的加工；MCP 工具返回的是**原始结果 JSON**（含 `include_original` 全文片段等）。`🟢` 若 AI 直接吃原始结果，**结构化来源引用需要在新方案里重建**，否则前端引用能力退化。

### 3.2 负向需求（内联 negative-requirement 分类，只取真实相关项）

| 分类 | 场景 | 期望行为 |
|---|---|---|
| **权限** | 模型（或用户提示词诱导）在参数里指定 `scope=其他项目`；或诱导调用 `delete-relation` | 结构性拒绝：`scope` 不在 schema 里（或强制覆盖为会话 scope）；写/删工具默认**不可见**，开启需显式授权 |
| **误操作** | 用户把 skill 提示词改坏 → AI 不再引用来源 / 开始编造 | ① 保存前**语法与必需规则检查**（如"反幻觉规则缺失"给警告）② 提供恢复默认 ③ 前端对"无来源的回答"保留可见降级标记 |
| **参数错误** | 提示词超长 / 空 / 含非法字符 | 复用现有 `SYSTEM_PROMPT_MAX_LEN` 校验 + 空值拒绝 + 明确错误文案 |
| **中途放弃** | 编辑到一半切走/刷新 → 内容丢失 | 草稿态保留或离开前提示；不得静默丢失 |
| **状态异常** | 保存了但**不生效**（缓存 / 仅新会话生效 / 需重启） | 明确"作用域 + 生效时机"并在 UI 上说明；保存后给出"已对下一次提问生效"的确认 |
| **数据异常** | MCP 工具返回错误 JSON / 超时 / 空结果 | 工具错误要作为**结构化结果**回给模型（现有 `tool_end.error` 已是这个模式），不得让对话崩掉 |
| **外部依赖** | MCP server 不可达 / 工具未注册 | 对话仍可用（纯聊天），并明确提示"知识库工具当前不可用"，不得静默以模型自身知识作答 |
| **越权读取** | 通过 `ki_scope_list` 枚举出全部 scope | ✅ 已接受（跨 scope 不再是风险）→ 降为"是否暴露该工具"的能力选择 |
| **敏感信息（R12）** | 工具参数/返回结构里可能含用户输入、知识库片段、本地文件路径 | 展示层做**脱敏与折叠**：默认收起、路径可截断；不落盘则零风险，落盘需评估 |
| **体积/性能（R12）** | 落盘完整返回结构 → 会话文件膨胀（现有 `sources` 已限 200 字/条） | 若落盘，只存**摘要 + 结构骨架**（字段名/条数/行号区间），不存全文 |

| 7 | **AI 走 MCP 的连接方式**：进程内直接调工具 handler ↔ 真走 MCP 协议（HTTP/stdio 自连） | 既有代码**明确写过"不绕 HTTP / MCP 自调用"**，本次是推翻它 → 需要理由与代价评估 | 进程内更简单更快；自连更"真"但多一次序列化与鉴权绕行 |
| 8 | 是否存在其他 MCP 消费方（IDE 客户端除外） | 影响面可能不全 | `⚪ 未发现（需确认）` |
| 9 | **R12 的落盘口径**：仅生成中可查（内存态）↔ 落盘摘要 ↔ 落盘完整 | 决定是否触碰 **N22 不变量** 与契约变更范围；也决定刷新后能否回看 | 看一次真实会话文件大小 + 你刷新后是否还需要查看 |

### 5.1 决策记录：scope 注入口径（2026-09-30 拍板）

**决策（用户 2026-09-30 原话）**：「跨 scope 查询没事。不传默认就是当前页面选中的 scope。」

**落地口径**（我的解读，请一句话确认）：

| 项 | 结论 | 依据 |
|---|---|---|
| 跨 scope 检索是否可接受 | ✅ **可接受**（本地单用户工具，不作为安全边界） | 用户拍板 |
| `scope` 值来源 | **页面当前选中**（作为默认值注入） | 用户拍板 |
| 模型能否传 `scope` | **不能**（剥离参数）—— 与上一轮"不让 AI 去传 scope"一致 | 用户上一轮拍板 |
| ⚠️ 备选口径待确认 | 若"不传默认"意味着**模型仍可传值覆盖页面值**，请明确一句 —— 那"防模型幻觉跨 scope"这条即放弃，只剩参数可读性收益 | ⚠️ 需确认 |

**执行前提（已写成 R11）：切页面 scope 时须同步切会话。** `🟢`

- 会话按 scope 分区落盘（`chatDir/{scope}/c-*.json`），会话列表也按 `scope` 查（`GET /conversations?scope=`）；
- 但 `resolveConversationInScopes` 会**跨全部 scope** 查找会话 id（`chat-routes.ts:228-245`，为区分 403/404）；
- 因此若前端切 scope 时保留旧 `activeConvId`，就会出现**历史消息属 A、检索打到 B** 的上下文错配（功能问题，非安全问题）；
- 正常 UI 流程（切 scope = 换会话列表）通常不触发 → 只需把这条**显式写进交互设计**。

**这个口径防什么 / 不防什么**（避免被当成安全边界）：

- ✅ 仍防：模型幻觉出 `scope` 并试图跨 scope 检索（参数被剥）
- ❌ 不再防、且**已被接受**：越权客户端指定 scope（跨 scope 本身已接受）
- ❌ 与写/删工具无关：那是 **P0#2** 的独立问题（详见 §1 第 3 条）

**能力说明**：`ki_search` 原支持"逗号分隔多 scope 聚合检索"。既然跨 scope 可接受，则**聚合检索也可作为可选能力保留**（由注入值决定是否展开多个 scope）—— 做不做，与 P0#2 一并定。

**给下游设计的实现约束（不变）**：① 工具 schema 层不暴露 `scope`（同现有 N23 做法，`retrieval-skill.ts:52-74`）② 执行层白名单取键（同 `kb-search-tool.ts:52,84-87`）。**不能只在执行层覆盖**——否则模型仍会看到该参数并反复尝试传它。

## 6. 关键假设

| ID | 假设 | 错了会怎样 | 验证方法 |
|---|---|---|---|
| A1 | 动机是**解耦 + 让用户可调**（而不是为了"能力对齐 IDE"） | 需求重心会偏：若目标是能力对齐，则应优先做工具集与参数可读性而非编辑 UI | 你一句话确认 |
| A2 | AI 的**写权限默认关闭**是可接受的 | 若你需要 AI 能"边聊边整理知识库"，则 R9/审批链要提前到 P0 | 你一句话确认 |
| A3 | skill 的形态就是**一段可编辑文本**（不是可执行插件） | 若期望"技能可执行/可参数化"，需换成更强的机制（沙箱、参数 schema） | 你一句话确认 |
| A4 | 提示词与 skill **共用一套编辑/存储**（不做两套） | 若两者生效范围不同，UI 与存储要分开设计 | 与待确认 5 一起定 |

**硬约束（来自现有代码与既有走查结论）** `🟢`
