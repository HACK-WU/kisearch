# agents-md-init AGENTS.md 初始化

> **前置条件**：AI 已了解 ki MCP 工具。AGENTS.md 位于项目根目录。
> **格式模板**：完整 AGENTS.md 模板见 [AGENTS-template.md](AGENTS-template.md)，本文件不内嵌模板。
> **边界**：本 skill 负责"结构与索引建对"（用户手动触发，**禁止 AI 自动触发**），并**承载记忆行为的完整口径**——主动沉淀（§2.5）、代码片段记忆（§2.6）、会话收尾自查与汇报格式（§2.7 / §2.7.1）。**每次对话都在场的那部分强制力**由用户级 alwaysApply 规则与 AGENTS.md 置顶章节提供，本 skill 本身按需加载、不常驻；上报执行层在 `use_skill("event-report")`。

---

## 1. 概述

**目的**：维护 AGENTS.md 的**结构与索引缓存**，确保索引信息与实际 ki 数据保持一致；并把「主动沉淀」（§2.5）与「知识文档入库」（§2.4）两条**运行期约定**写进文件，让它们在每次对话的上下文里都在场。同时作为**记忆行为口径的唯一真源**：沉淀粒度与查重（§2.5）、代码片段格式与分类（§2.6）、会话收尾自查与收尾汇报格式（§2.7 / §2.7.1）、近期工作归档（§5）都在本文件定义。历史上为解决"规则文件内嵌模板导致内容混乱"而拆出 skill，2026-11-19 起原 `rules/ai-codekb-memory.md` 的有价值内容并入本文件，规则文件下线。

**功能**：
- 用户手动触发时创建/重建 AGENTS.md 的结构（如用户说"初始化 AGENTS.md"、"刷新索引缓存"）
- 判定目标项目记忆 scope（`${scope}-memory`），多候选时不擅自全量写入（见 §2.0）
- 查询 ki 获取真实索引数据填充项目记忆索引，**以 `ki_group_list` 输出为权威机械转写**（见 §2.3）
- Group 骨架按需补建，其余交由 `ki_sync_relation` 自动补建（不必逐个预建，见 §2.1）
- 同步「团队约定」Group 内容到 AGENTS.md"团队约定"章节（空则写"无"，见 §3.6）
- 代码知识库（`${scope}`）索引不写入 AGENTS.md，查询走 `ki-search` 直连 ki
- 用户画像与近期工作章节的**结构**在此建立；条目增删与 7 天归档口径见 §5
- **置顶写入「第一原则：遇事不决，先取文档（ki_recall → ki_search）」**——**拿到新任务的第一动作是 `ki_recall` 预取「该读哪几篇」，按清单读正文再动手，之后才用 `ki_search` 查证**；`ki_recall` 不可见时降级为直接 `ki_search` 并如实说明；同时提示「跨库检索前先 `ki_view_list` 看视图」（视图会变，**不缓存列表**、每次实时查，见 §2.1 ⑧ / §8 禁忌 23）
- **置顶写入「安全底线：代码与测试禁止敏感信息」**——私钥、线上地址、真实 IP、账号口令、个人信息一律用占位符（见 §2.1 ⑨ / §8 禁忌 16）
- **置顶写入「第二原则：主动沉淀，不等提示」**——开发 / 设计 / 排查过程中产生的信息、决策、设计，AI **自己**写进 `${scope}-memory`，**用户开口不是触发条件**（见 §2.5 / §2.1 ⑩）
- **同节写入「上报触发行」**——分流（结论 → 记忆 / 一件事 → 事件）+ `use_skill("event-report")` + 对话回执 + 文档三分法（产物挂 `docs` / 证据挂 `refs`）；**执行层在 `event-report`，本 skill 只写触发约定**（见 §2.1 ⑩ / §2.2 ⑦ / §7）
- **置顶写入「第三原则：预取细则」**——它是**第一原则第一步的执行细则**（任务画像四要素、`nextActions` 怎么读、`skipped`/`degraded` 怎么如实说），顺序由第一原则定义，本节不重复定义；**仅当会话工具列表里存在 `ki_recall` 时写入**（能力探测见 §2.1 ⑫ / §2.2 ⑨），工具不存在时**不写**，否则等于指导 AI 调用不存在的工具
- **置顶写入「第四原则：收尾汇报」**——任务或阶段给出交付结论前，按四要素（+ 条件要素「文档链接」）给一段精炼汇报（状态变更 / 沉淀落点 / 剩余边界 / 待用户决定 / ⑤ 文档链接）；格式真源在 §2.7.1，写入与核对见 §2.1 ⑬ / §2.2 ⑩
- **定义「主动沉淀」约定**：什么该沉、落哪个 Group、粒度与查重、**通道选择（短内容走 `ki_sync_relation`，本地成篇文档走 `use_skill("ki-upload")`）**、写完怎么验证、什么不该沉，以及三个记忆系统之间的分工（见 §2.5）
- **定义「文档健康维护」约定**：发现**过时或描述错误**的文档（AGENTS.md 自身章节 / `${scope}-memory` 记忆与文档 / 项目内文档）时**主动修正或删除**，不让错误知识留在检索第一线；先改后删、被推翻的判断不删、删除留痕（见 §2.8）
- **定义「代码片段记忆」口径**：预定义 Group 树、分类原则、片段格式铁律、从代码批量构建的识别规则、与代码知识库的边界（见 §2.6）
- **定义「会话收尾自查」清单与「收尾汇报」输出格式**：自查未漏记录 / 未漏上报 / 未漏收口 / 未漏归档 / 未漏贴文档链接（§2.7），再按四要素 + 条件要素输出（§2.7.1）
- **`ki` CLI / MCP 工具行为异常必须当场汇报**，不静默重试、不自愈式绕过（见 §1.6 / §8 禁忌 17）
- **定义「知识文档入库」约定**：哪些产出的文档该上传进 `${scope}-memory`、落哪个 Group、怎么验证、怎么回填（见 §2.4）；实际传输能力由 `use_skill("ki-upload")` 提供，本 skill 不重写其参数与错误码（见 §7）
- 无真实数据时用示例格式兜底（标注 ⚠️）

**使用场景**（用户手动触发）：
- 首次对话，用户要求初始化 AGENTS.md
- 索引变更后用户要求刷新缓存
- 手动触发"初始化 AGENTS.md"、"刷新缓存"
- ki 中无任何 scope 时引导用户创建
- **开发 / 设计 / 排查过程产出了可复用文档**（设计文档、排查结论、调研报告、上线手册），需要沉淀成可检索的项目记忆 → 按 §2.4 走 `use_skill("ki-upload")` 入库
- 用户说"这份设计文档入库 / 传到 ki / 沉淀一下" → 先按 §2.4 判定该不该传、传哪个 Group，再执行上传
- 用户说"以后决策/设计自己记进 ki，别等我提醒" → 按 §2.5 口径把「第二原则：主动沉淀」补进 AGENTS.md（写入动作同 §2.1 ⑩ / §2.2 ⑦，不必改 skill 本体）
- 需要查"记忆该怎么写 / 收尾怎么汇报"的口径（落哪个 Group / 代码片段什么格式 / 收尾查什么 / 汇报四要素 + 文档链接 / 三个记忆系统怎么选）→ 直接读 §2.5 / §2.6 / §2.7 / §2.7.1，不必触发初始化

## 1.5 首次使用引导

> **当 `ki_scope_list` 返回空列表时，AI 应主动引导。**

```
① ki_scope_list → 无任何 scope（或本项目尚无 memory scope）
    ↓
② 主动提示用户：
    "检测到项目尚未配置 ki 索引。是否需要我帮你初始化？"
    ↓ 用户确认
③ 确定 memory scope 名称（默认 `${项目目录名小写}-memory`，判定口径见 §2.0）
④ ki_group_create(scope: "<memory scope>", path: "背景与目标")
    # scope 不存在时该工具会自动创建并返回 createdScope，无需单独建 scope
    # 其余 Group 不必逐个预建：ki_sync_relation / ki_bulk_sync_relation 会按写入路径自动补建
⑤ 执行完整初始化（步骤 2.1）
```

> 用户拒绝则跳过，后续按需触发。
> 用户画像与近期工作不创建对应 scope/Group——直接写入 AGENTS.md 的"用户画像"/"近期工作"章节。
> **不要给代码知识库（`${scope}`）建「项目概述」等组**：代码库索引不写入 AGENTS.md，本 skill 也不维护它，建出来只会是空壳（历史实证：某项目 scope 仅剩一个 wikiCount 0 的「项目概述」空组）。

### 异常处理

若本 skill 文件不可用（如新克隆项目）：跳过 AGENTS.md 初始化，后续用户明确要求时再按需处理（kisearch 缺失时引导用户先安装 ki）。

## 1.6 ki 工具异常上报（必做）

> 本 skill 全程依赖 `ki` CLI 与 MCP 工具。**它们报错、或"跑通了但不像应该的样子"时，当场向用户汇报，不得静默重试或换路绕过。**

**触发条件**（任一命中即算异常，不以"最终能跑完"为标准）：

| 类型 | 例子 |
|------|------|
| 失败 | 报错、非零退出、超时/挂起；**即使重试后成功，首次失败也要说** |
| 结果不符 | 写入成功但 `ki_group_list` 查不到；`ki_search` 返回条数与 `limit` 不一致；scope / Group / Relation 名被改写；字段缺失或类型不对 |
| 违背承诺 | 与工具描述或本 skill 口径矛盾：该自动补建 Group 的没补、多级路径父组未校验、所谓幂等写入却重复叠加 |
| 静默降级 | 该失败却返回空列表 / `- 暂无`；部分成功却报全成功；被截断/被收敛无任何提示 |
| 输出污染 | 进度条、日志混进 stdout 破坏可解析输出；编码/换行错乱 |

**汇报格式**（一次给全，不要挤牙膏）：

- 工具与命令：`ki_xxx(...)` / `ki <子命令>`
- 入参：完整参数（含 scope / group / limit，敏感值脱敏）
- 实际：原始输出关键行 或 退出码
- 预期：按工具描述、`docs/cli.md` 或本 skill 应有行为
- 影响：本次流程哪一步不可信、是否已阻塞、是否影响已写入的索引
- 已试：重试次数与结果、是否已绕过（默认不绕过）

**禁止**：

- 静默重试把异常掩盖成"正常"；只在收尾时飘一句"中途有报错但已解决"
- 改参数 / 换工具 / 手改文件绕过异常后把流程跑完，不告知用户
- 把可疑输出当权威数据**机械转写**进 AGENTS.md（宁可停下等结论，不写入不确定的索引，见 §2.3）

## 2. 初始化流程

> **仅当用户明确说明要初始化或刷新 AGENTS.md 时才执行，禁止 AI 自动触发。**

### 2.0 目标 memory scope 判定（必做）

> **背景**：`ki_scope_list` 返回的是本机全部 scope（实测同一台机器可有 100+ 个，其中多个 `*-memory` 并存）。**"对每个 `${scope}-memory` 都写一节"是错的** —— 会把历史测试 scope 与其他项目的项目记忆写进本项目的 AGENTS.md。

**判定顺序**（命中即停）：

```
① AGENTS.md 已存在且"项目记忆索引"章节已记录 memory scope 名？
    ├─ 是，且 ki_scope_list 里仍有该 scope → 直接沿用（缓存自证，不重新推断）
    └─ 是，但 ki 里已不存在（被删/改名）→ 回到 ② 重新判定，并告知用户"原记录的 X 已不存在"
② 只有一个 scope 带 -memory 后缀？
    └─ 是 → 用它
③ 多个候选 → 依次过滤：
    ├─ 保留 registered: true 的（在配置中正式注册）
    ├─ 保留与项目目录名 / git 仓库名有词根重合的（如目录 xpert ↔ scope xpert-memory）
    └─ 仍剩多个 → 问用户一次："本项目项目记忆用哪个 scope？候选：A / B"，不猜
④ 判定结果写入 AGENTS.md 索引章节首行（`数据来源：ki 的 <scope> scope`），供下次会话直接沿用
```

**边界**：只在"初始化 / 重建"时判定；日常增量维护（§2.5）沿用 AGENTS.md 已记录的值，不重新判定。

**路由**（均需用户明确要求，禁止 AI 自动触发）：

```
用户明确要求后
    │
    ├── AGENTS.md 不存在？
    │       └── 是 → 执行完整初始化（步骤 2.1）
    │
    ├── AGENTS.md 存在但无"项目记忆索引"章节？
    │       └── 是 → 执行完整初始化
    │
    └── AGENTS.md 存在且完整？
            └── 检查索引一致性 → 不一致则增量更新
```

### 2.1 完整初始化

```
① 判定目标 memory scope（§2.0）→ 得到唯一 scope
② ki_group_list(scope: <目标>, mode: "full", depth: 4)
     → Group 结构（权威源，含各层子组）
③ ki_group_list(scope: <目标>, mode: "hot", hot_count: 3)
     → 热门 Relation（Top 3）
④ Group 骨架补建：只补本 skill 需要立即展示的最小集
     - 「团队约定」必建（§3.6 依赖它做同步源）
     - 其余按模板清单与 ② 的差集补，且只补"首层必要项"；不必一次建满 12~18 个
     - 工具：ki_group_create(scope, path)；parent 必须已存在，多级路径先建父
⑤ 同步「团队约定」Group → 填充 AGENTS.md"团队约定"章节（Group 为空则写"无"，见 §3.6）
⑥ 用户画像与近期工作章节 → 建立章节骨架（空模板，预置维度按需，不硬造内容）
⑦ 写入 AGENTS.md（参考 AGENTS-template.md）：
     ② ③ 的输出**机械转写**进"项目记忆索引"，禁止自由摘要（见 §2.3）
⑧ 核对置顶「第一原则」：AGENTS.md 标题下第一个章节必须是
     「## 🔑 第一原则：遇事不决，先取文档（ki_recall → ki_search）」，正文含
     ① **第一动作是 `ki_recall` 预取**（不可见时降级为直接 `ki_search` 并说明）
     ② 查询顺序 ③ **跨库检索前先 `ki_view_list` 看视图** ④ 视图只读不可写入
     缺失即补；**这是初始化必做项，不是可选项**；**老文件标题为「遇事不决，ki-search」的，一并改写为新标题**
⑨ 核对置顶「安全底线」：文件头部说明块必须含一句
     "**本文件与一切代码、测试禁止写入敏感信息**（私钥/证书、线上地址、真实 IP、
      账号口令/Token、个人信息），示例一律用占位符"，缺失即补；**同为初始化必做项**
⑩ 写入「主动沉淀」章节（运行期约定，见 §2.5），位置**紧随「第一原则」之后**
     · 标题固定 `## 📝 第二原则：主动沉淀，不等提示`
     · 只写约定（何时沉 / 落哪个 Group / 写前查重 / **两条通道：MCP 与 `ki-upload`** /
       写后验证 / 不写什么），**初始化阶段不写任何记忆内容**
     · 必须含**上报触发行**：分流（结论 → 记忆 / 一件事 → 事件）、`use_skill("event-report")`、
       对话回执要求、文档三分法（产物挂 `docs` / 证据挂 `refs`，见 §2.5 二 / §7）
     · 必须含**文档健康行**：发现过时 / 描述错误的文档 → 能改就改、确认无用才删、删除留痕（§2.8）
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写
⑪ 写入「知识文档入库」章节骨架（运行期约定，见 §2.4）
     · 只写约定，**初始化阶段不扫描、不上传任何文档**
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写
⑫ 核对「第三原则：预取细则」（**能力探测后才写**）
     · 探测：当前会话的工具列表里是否存在 `ki_recall`（MCP 客户端可见即算）
     · **三档判据（缺一档就会静默漏写）**：
         - 看得到 `ki_recall` → 写入
         - 看不到 `ki_recall`，但看得到 `ki_ask` → 服务端版本较旧（有模型消耗型工具却无本工具）
              → 跳写，并在「更新日志」记一行「ki 侧未提供 ki_recall，第三原则跳写」
         - **连 `ki_ask` 都看不到** → 当前多半是**只读 Token 会话**（模型消耗型工具整体不可见，
              而 `ki_recall` 正属此类）⇒ **不能判定服务端有没有**：
              不静默跳写，提示用户「当前会话为只读，无法确认 ki_recall 能力；如需写入第三原则，请用读写 Token 重跑本 skill」
         - 已存在该节但工具已不可用 → **保留章节并提示用户**（可能换了 ki 实例），不静默删除
     · 位置：**安全底线之后、「项目记忆索引」之前**；标题固定 `## 🔎 第三原则：预取细则（ki_recall）`
     · 首句须写明「本节是第一原则第一步的执行细则，顺序由第一原则定义」；**老标题「开工前预取（ki_recall）」一并改写**
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写；**不写本项目源码路径**（禁忌 24）
     · 只写约定，**不在初始化阶段替用户跑任何预取**
⑬ 写入「第四原则：收尾汇报」（运行期约定，见 §2.7.1）
     · 位置：**第三原则之后（第三原则跳写时紧随安全底线）、文件头说明块之前**；标题固定
       `## 🧾 第四原则：收尾汇报（做了什么 / 落了什么 / 剩什么 / 等你定什么）`
     · **无条件必写**（不依赖任何 MCP 工具，与 ⑫ 的能力探测无关）
     · 只写四要素 + 条件要素与触发时机（状态变更 / 沉淀落点 / 剩余边界 / 待用户决定 / ⑤ 文档链接：写到末尾的 `[文档名称](url)`），**不写汇报样例正文**
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写
```

> **⑩ ⑪ ⑫ ⑬ 的存在理由**：AGENTS.md 是每次对话全量注入的上下文，运行期 AI 读得到这些约定才会照着做；只写在 skill 里（用户手动触发才加载）等于没人看得见 —— 「主动沉淀」尤其如此：**没人在上下文里提醒，AI 就会等用户开口才记**；「收尾汇报」同理：不写进置顶区，AI 就只在被要求时才总结。

> 代码知识库 `${scope}` 的索引不初始化到 AGENTS.md，仅缓存 `${scope}-memory` 项目记忆索引。
> **不预建空 Group**：`ki_sync_relation` / `ki_bulk_sync_relation` 写入时都会**自动补建缺失的 Group 树**（多级路径的父组一并创建），写入后自然成形；而 `ki_group_create` 只能单个建、没有批量工具，预建 12+ 个组是纯调用成本。

### 2.2 增量更新

当 AGENTS.md 已存在但部分过期时：

```
① 读取 AGENTS.md，取其中已记录的 memory scope 名（§2.0 ①，不再重新推断）
② ki_scope_list → 确认该 scope 仍存在（不存在 → 提示用户，不静默改写）
③ 漂移自检（本次核心）：以 ki 为权威，与文件逐项比对
   - Group 结构：ki_group_list(mode: "full") 的每个组/子组 ↔ 索引章节的列表项
       · ki 有、文件无 → 补
       · 文件有、ki 无 → 删（组已被删除）
   - 热门 Relation：mode: "hot" 的结果 ↔ "热门 Relation" 小节
   - 团队约定：ki_group_list(groups: "团队约定", mode: "full") ↔ "团队约定"章节
④ 检查"近期工作"时间戳与条目数（> 7 天 / 超过 ~20 条 → 触发归档，规则见 §5）
⑤ 用户画像：保留已有内容，仅当出现新维度时补充小节
⑥ 核对置顶「第一原则」与「安全底线」是否存在（同 §2.1 ⑧ ⑨，缺失即补；老文件普遍缺这两条，且第一原则多缺视图提示）
⑦ 核对「第二原则：主动沉淀」章节是否存在（同 §2.1 ⑩；老文件普遍没有，缺失即补，
   **只补约定不补记忆内容**；已有但缺"不等用户提示"这条硬话的，补齐；
   **并核对上报触发行**——缺「分流 / `use_skill("event-report")` / 回执 / 文档三分法（产物挂 docs、证据挂 refs）」中任一项即补；
   **并核对文档健康行**——缺「过时 / 描述错误文档 → 能改就改、确认无用才删、删除留痕」一条即补（§2.8））
⑧ 核对「知识文档入库」章节是否存在（同 §2.1 ⑪；老文件普遍没有，缺失即补，**只补约定不补上传**）
⑨ 核对「第三原则：预取细则」章节（同 §2.1 ⑫，**按三档判据探测，不得只看一眼工具列表**）：
   可见 → 缺则补；不可见但看得到 `ki_ask` → 服务端旧版本，跳过并记日志；
   连 `ki_ask` 也不可见 → 只读会话，**提示用户换读写 Token 重跑**，不静默跳过
⑩ 核对「第四原则：收尾汇报」章节是否存在（同 §2.1 ⑬；**无条件必写**，与 `ki_recall` 探测无关，
   老文件普遍没有）：缺则按模板补；已有但只写了自查没写"四要素输出"的，补齐（含 ⑤ 文档链接这条条件要素）；**只补格式约定不补样例内容**
⑪ **保留项目专属置顶章节**：第一~第四原则之外的置顶章节（如 `## 📦 第五原则：…`）
   属于项目自定内容，模板不定义 —— **原样保留，不删不重排**（刷新时最容易把这类章节
   当成"模板里没有的冗余"裁掉）
⑫ 结构性变更写入"更新日志"（仅结构变更，见 §6）
```

> **③ 的方法论**：比对必须"机械"——把 `ki_group_list` 的树输出逐行映射成列表项，而不是读完凭印象重写。历史实证：某项目初始化后新增了 2 个组（错误库、决策记录）和 1 个子组，靠印象摘要的索引连续数周未发现缺失，同期"热门 Relation"一直写着"暂无"而实际已有 3 条热区数据。

### 2.3 机械转写规则（防漂移）

| 数据源 | 转写方式 | 禁止 |
|--------|---------|------|
| `ki_group_list(mode: "full")` | 树形缩进逐层映射为嵌套列表，组名原样照抄 | 合并同类组、省略"看起来空"的组、改写成业务名称 |
| `ki_group_list(mode: "hot")` | 每条一行：`- {Group}/{Relation} (score: {n})` | 无数据时编造；空热区写 `- 暂无` 并注明日期 |
| `ki_group_list(groups: "团队约定")` | 每条压成一行要点 `- {Relation}: {一句话}` | 全文转储；空组留空（必须写 `- 无`） |

> 索引章节首行固定写 `> 数据来源：ki 的 <scope> scope（YYYY-MM-DD 初始化）`，供下次会话判定目标 scope 与判断缓存新旧。

**折叠条款（唯一例外，判据机械）**：组路径中**含独立 `文档` 段**（如 `错误库/文档`、`错误库/文档/sub`）的组是 `ki-upload` 批量导入的文档（§2.4 约定）。这类组折叠成一行且**附前 3 篇篇名**（保住可发现性），形如 `- 错误库/文档（12 篇：OOM 排查、端口冲突、依赖装不上…）`，不逐条展开 relation。

> **为什么必须折叠**：一篇文档 = 1 个 relation，几十篇就是几十行；AGENTS.md 是**每次对话全量注入**的上下文，索引撑大会把"缓存"变成负债。
> **边界**：判据只有一个——**组路径里有独立的 `文档` 段**（段级匹配，`文档规范` 这类子串不算；源目录带子目录时落点延伸成 `文档/sub`，判据仍成立）。手写记忆的组不得折叠；若该 `文档` 段已被**手写** relation 占用，导入改用 `文档归档` 段并在本节写一行说明，避免手写内容被误折叠。

### 2.4 知识文档入库（运行期约定，非初始化动作）

> **初始化不扫描、不上传任何文档**。本节定义的是**运行期**该怎么做：AI 在开发 / 设计 / 排查 / 调研中产出了可复用文档，把它沉淀成 `${scope}-memory` 里可检索的记忆。
> 初始化只把这套约定写进 AGENTS.md（§2.1 ⑪）；实际传输由 `use_skill("ki-upload")` 完成（参数、错误码、脚本用法以它为准，见 §7）。
> **与 `ki-upload` 同时被触发时，scope 与 `--group` 以本节为准**——它默认按源目录推导 group，恰好不满足本节要求。

#### 一、什么时候该传（判据）

| 该传：有复用价值的结论性文档 | 不该传 |
|---|---|
| 设计文档、技术方案、API 设计 | 源码、配置、构建产物 |
| 需求报告、调研报告、模块讲解 | 临时草稿、试验片段、TODO 清单 |
| 排查结论 / 根因分析（`.debug/*/evidence.md` 的**结论部分**） | 原始日志、截图、大数据样本 |
| 上线 / 回滚 / 迁移手册 | 已过期的一次性过程记录 |

**一句话判据**：*换个会话、换个人，这份文档能不能省掉一次重复调研？* 不能就不传。

#### 二、落点与 Group

- **scope 固定 `${scope}-memory`**：与 AGENTS.md 同库，检索时一次 `ki_search` 同时命中记忆与文档
- **`--group` 必填，且路径里必须有一层叫 `文档`** —— 这是索引折叠的机械判据（见 §2.3）。留空会按源目录推导，落点不可控；源目录带子目录时会自动延伸成 `错误库/文档/sub`，判据仍成立
- 归类按文档性质（不查固定表，落到"将来谁会读到它"的那个组）：

```
设计 / 方案      → 专题记忆/{模块名}/文档
根因 / 踩坑      → 错误库/文档  或  项目踩坑点/文档
架构 / 数据流    → 项目架构/文档 或 数据流/文档
决策与取舍       → 决策记录/文档
无合适归类       → 通用记忆片段/{分类}/文档
```

> 导入（`ki import` / `ki-upload`）会自动建组，**不必先 `ki_group_create`**。

- **不要留空 `--group`**：单文件上传留空落根组 `__root__`、目录上传按子目录推导——两种都不含 `文档` 段，索引里无法归类也无法折叠

#### 三、通道选择（本机文档一律走 ki-upload）

| 情形 | 通道 |
|------|------|
| 本机文档 → 远端 ki（**默认**） | `use_skill("ki-upload")` 的 `upload` / `upload-dir`：跨机可用、自动切分 + 向量化 |
| **属于某个事件产出的文档**（debug 报告 / 需求报告 / 复盘） | 同上，额外带 `--lifecycle event --event '#N'`：上传即挂成该事件的 `docs`（分类随阶段）。已有文档则用 `ki_event_edit(action="members", docAction="add", docRefs=[...])` 事后补挂 |
| 正文已在上下文里且很短（一段结论） | MCP `ki_sync_relation` 逐条写（**不做 chunk 切分，长文档别用**） |
| 文件与 ki 同机 | `ki import --source <dir> --scope ${scope}-memory --group <g>` |

> **事件产物 vs 普通文档**：判据以 `use_skill("event-report")` §5 为准 —— *这件事收口之后，这份文档还有独立存在的意义吗？* 有 → 按上面的落点与折叠规则当普通文档传；没有 → 它是事件产物，挂 `docs`（改分类、随阶段）。**顺序是「先挂 docs，再推终态」**，已收口的事件挂不了。
> 事件产物允许落在 `事件参考` 这类不含 `文档` 段的组（不会触发 §2.3 的折叠），因为它们由事件页承载，不靠 AGENTS.md 索引发现。

#### 四、上传后必做两步

1. **验证**：`ki_search(scope: "${scope}-memory", query: "<文档里的一句话>")` 命中，**或至少** `ki_group_list` 能看到该 relation 名 —— **上传成功 ≠ 可检索**；`--no-vector` 时只有全文索引，别只靠语义分判断
2. **回填**：「近期工作」记一行 `- [YYYY-MM-DD] ✅ {文档/目录} 已入库 {Group}`（≤ 80 字，见 §5）

#### 五、环境不全时降级（不得阻塞）

缺 Python ≥ 3.11 / `httpflex` / `KI_URL` / `KI_TOKEN` 任一项 → **不报错、不卡住当前任务**，改为给命令：

```
⚠️ 本地缺上传能力（{缺什么}），{文档} 暂未入库。出路：
   ① use_skill("ki-upload") → 按其「前置条件」装依赖后重跑
   ② 在 ki 同机执行：ki import --source <dir> --scope ${scope}-memory --group <g>
```

> 上传过程报错（`OPEN_API_*` 码、体积超限、`VECTOR_UNAVAILABLE`）→ 按 `use_skill("ki-upload")` 的「失败处理」表定位，**不得自行改脚本参数绕过**。

#### 六、与索引的关系（影响 §2.3 转写）

**上传的每篇文档 = `${scope}-memory` 某 Group 下 1 个 relation**（文件名去 `.md`，如 `DESIGN.md` → `DESIGN`），会真实出现在 `ki_group_list` 输出里 —— 不是"看不见的附件"。所以：

- Group 路径必须含 `文档` 段，让索引能机械识别"这一组是批量导入的文档"
- 这类组在索引章节**按篇数折叠成一行**，不逐条展开（见 §2.3 折叠条款）

### 2.5 主动沉淀：开发 / 设计 / 排查中产生的信息与决策（运行期约定，非初始化动作）

> **初始化不写任何记忆内容**。本节定义**运行期**口径：AI 在开发 / 设计 / 排查过程中产生的**信息、决策、设计**，必须**由 AI 自己**写入 `${scope}-memory`。
> **硬性口径：用户开口不是触发条件。**「等用户说'记一下'」「收尾时统一补记」都属于本条要禁止的漏写。
> 初始化只把这条约定写进 AGENTS.md（§2.1 ⑩）；写入工具参数与粒度见本节三，代码片段的分类与格式见 §2.6，归档见 §5。

#### 一、判定口径（必须现在写，不能攒）

**触发条件是「对话里出现了一条将来还有人要用的结论」，不是「用户要求记录」。**

| 自检 | 结论 |
|---|---|
| 换个会话、换个人接手，这条结论还用得上吗？ | 用得上 → **现在就写** |
| 不写会怎样？ | 下次要重新调研 / 重新问人 / 重新踩一遍坑 → **现在就写** |
| 只是一次性试错、中间状态、随时会被推翻的猜测？ | 不写（等结论稳定；被推翻的旧判断才值得写一句） |

> **不许"先干活，最后统一补记"**：收尾补记在实践中会被截断、被遗忘、被压缩成一句话而丢掉细节。写完一段就落一次。

#### 二、触发 → 落点（按性质归类）

| 对话中出现 | 落点 Group | Relation 命名 |
|---|---|---|
| 技术选型、方案取舍、被推翻的旧判断 | `决策记录` | `{决策主题}` |
| 架构分层、模块职责、依赖方向 | `项目架构` | `{模块名}` |
| 数据流、存储模型、字段口径 | `数据流` | `{链路 / 业务域}` |
| 接口契约、入参返回、错误码 | `接口信息` | `{模块}` |
| 报错根因、踩坑与解法 | `错误库` 或 `项目踩坑点` | `{现象 / 报错关键词}` |
| 某模块怎么用 + 内部实现要点 | `专题记忆/{模块名}` | `{子主题}` |
| 团队约定、提交规范、分支策略 | `团队约定` | `{约定名}` |
| 外部系统、SDK / API 限制 | `外部依赖` | `{依赖名}` |
| 可复用工具函数、脚本要点 | `工具库` | `{分类}` |
| 项目阶段、里程碑、当前状态口径 | `当前状态` | `{阶段}` |
| 以上都不合 | `通用记忆片段/{分类}` | `{分类}` |
| **越界发现、待办、要有人跟到收口的事**（bug / 技术债 / 缺失功能 / 文档过期） | **不进 relation，走事件** | `use_skill("event-report")` 上报为事件（判据与本 skill 的分流一致，见 §7） |

> `专题记忆` 组下**必须先建子组**再写 relation（团队约定，系统不校验）。
> 写入路径会自动补建父组，**不必先 `ki_group_create`**。

#### 三、粒度与查重（写坏了比不写更糟）

- **一条 Relation = 一个主题**，正文写「做什么 / 怎么用 / 为什么这么定 / 边界与坑」，不写过程流水账
- **写前必查**：先 `ki_get_module_info` 取回当前正文 —— `ki_sync_relation` 是**整篇覆盖、无追加语义**，直接写第二条会把第一条冲掉；同主题**改**，不同主题才**新建**
- 单条用 `ki_sync_relation`；**≥3 条用 `ki_bulk_sync_relation`**，每批 ≤5 条
- **只改长 Relation 里的几行** → `ki_edit_relation`（`edit` 多轮改行 → `view` 轮询 → `finish` 提交），别为了几行重写整篇；finish 是异步的，且会把正文覆盖写回源文件
- 正文控制在 1000 字符内，超长拆 Relation（超长会被警告且检索质量下降）

#### 四、通道选择：短内容走 MCP，成篇文档走 `ki-upload`

> **沉淀不等于"写 relation"**。正文已在上下文里、只有一段结论 → MCP 工具最快；**已经在本地写好的成篇文档 → 直接上传更省事、检索质量更好**。

| 形态 | 通道 | 理由 |
|---|---|---|
| 一条结论 / 一个主题（几百字 ~ 1000 字符） | `ki_sync_relation`（≥3 条用 `ki_bulk_sync_relation`，每批 ≤5） | 内容已在上下文，直接写最快 |
| **本地已写好的成篇文档**——设计文档、方案、排查报告、调研报告，**内容多的（如 500+ 行）** | `use_skill("ki-upload")` 的 `upload` / `upload-dir` | 自动切分 + 向量化；500 行塞进 relation 必然超长（>1000 字符警告）、检索质量差，还要手工复制粘贴 |

- **怎么选**：一段话能说清、将来只需被检索到一两句 → relation；**有章节结构、需要翻页、达到几百行** → 上传（别因为"上传要装依赖"就改塞 relation，装不上按 §2.4 五 降级给命令）
- **不要"先摘要再写 relation"**：原文直接上传，摘要压缩成「近期工作」一行即可
- **落组必须含 `文档` 段**（如 `专题记忆/{模块名}/文档`、`错误库/文档`），索引才能机械折叠（§2.4 二 / §2.3 折叠条款）
- **上传后验证、缺上传能力时的降级、文件与 ki 同机改走 `ki import`**：与 §2.4 三 / 四 / 五 同一口径，照其执行，本节不复述（避免两套账漂移）

#### 五、写完之后（必做两步，缺一不可）

1. **刷新索引**：AGENTS.md「项目记忆索引」按 `ki_group_list(mode: "full")` 机械转写（§2.3）；写的是「团队约定」组时**同时回刷** AGENTS.md「团队约定」章节（§3.6，空则写"无"）
2. **留一行痕迹**：AGENTS.md「近期工作」记 `- [YYYY-MM-DD] {一句话结论}`（≤ 80 字，详情留在 ki）；**追加后立即数条目数，> 20 条即按 §5 T1 归档**

#### 六、不写什么（边界）

| 不写 | 原因 |
|---|---|
| 用户画像、需求进度 | 只进 AGENTS.md（§3.5），进 ki 会重复且查不到 |
| 一次性调试过程、临时试错、废弃方案过程 | 没有复用价值；结论稳定后的取舍写 `决策记录` |
| 敏感信息（私钥、线上地址、真实 IP、真实账号） | 一律占位符（§8 禁忌 16） |
| `${scope}`（代码知识库） | **默认只读**，需用户明确授权；新知识一律先写 `${scope}-memory` |

> **库名未定 / 未初始化**：目标 scope 以 AGENTS.md 索引章节首行登记为准（§2.0）；项目尚未初始化（无 memory scope）→ 先按 §1.5 引导，**不臆造 scope 名**，也不改写 `${scope}` 代码知识库。

#### 七、三个记忆系统怎么选

| 系统 | 装什么 | 判据 |
|---|---|---|
| 平台内置记忆（`update_memory`） | 简洁、通用、跨项目、稳定的偏好 | 换个项目还成立的沟通偏好 / 工具习惯 |
| `ki`（`${scope}-memory`） | 详细、项目特定、结构化、有时效 | 要查得到、要有人接手、可能被推翻的知识 |
| `AGENTS.md` | 摘要 + 索引缓存 + 用户画像 + 近期工作 | 必须每次对话都在场的一行结论与结构 |

- **偏好再切一刀**：跨项目工具偏好（编辑器 / 包管理器 / 终端）→ 平台记忆；项目特有偏好（命名约定 / 分支策略）→ AGENTS.md「用户画像」
- **记忆失实**：发现记忆与实际代码不一致 → **更新**对应 Relation（不是追加新条目），过时 / 描述错误内容的完整判据与删除口径见 §2.8；只动 `${scope}-memory`，`${scope}` 代码知识库仍需授权（§2.5 六）
- **禁止**用平台记忆 MCP（`memory_store` / `memory_search`）读写 ki 数据——两套存储不通，会造出孤儿数据

### 2.6 代码片段记忆：函数 / 流程 / 数据模型级的要点（运行期约定，非初始化动作）

> 与 §2.5 分工：§2.5 管"什么该沉、落哪个 Group"；本节管**片段长什么样**——格式写错会让语义检索命不中。

**预定义 Group（优先归类）**

```
工具库/          ← 通用工具函数、脚本
项目踩坑点/      ← 已知问题、注意事项
部署运维/        ← 配置模板、部署流程
通用记忆片段/    ← 兜底，与前三者平级
├── 关键逻辑/    ← 主流程、状态机
├── 数据模型/    ← interface / type / class
├── API 调用/    ← HTTP 封装
├── 配置模板/    ← 配置、枚举、常量
└── 错误处理/    ← 错误处理、降级
```

- **分类原则**：优先归入预定义 Group；无匹配走 `通用记忆片段` 并按业务功能或代码类型细分；单 Relation 超 10 个片段就拆分
- **与团队约定的边界**：`团队约定` / Commit 规范等**项目级约定** → `${scope}-memory`（团队约定）；lint 规则、纯代码约定 → `${scope}`（见 `ki-search` 白名单）。拿不准默认走 `${scope}-memory`

**片段格式铁律**

> 正文**第 1 行必须是纯文字描述**（1-2 句，说明"做什么、怎么用"）；**禁止 `###` 标题开头、禁止 YAML frontmatter**——标题语义量低且干扰向量化。必填 `符号`（类 / 方法签名）与 `位置`（文件路径，**不写行号**：行号随代码变动失效）。

```markdown
将 Date 对象格式化为 yyyy-MM-dd 字符串的通用工具函数，支持自定义分隔符。
- 符号: `DateUtils.formatDate(date: Date, separator?: string): string`
- 位置: `src/utils/date.ts`
- 用法: `DateUtils.formatDate(new Date())` → `"2026-06-23"`
```

> 示例里的 `src/utils/date.ts` 是**格式占位**，与本项目结构无关（禁忌 24 同口径：只写格式，不写本项目真实路径）。

**从代码构建片段记忆（用户明确要求时）**

1. 扫描代码，识别可复用函数 / 类 / 方法
2. 分类：工具函数（无副作用、通用）→ `工具库`；核心执行逻辑 → `通用记忆片段/关键逻辑`；interface / type / class → `数据模型`；HTTP 封装 → `API 调用`；配置 / 枚举 / 常量 → `配置模板`；错误处理 / 降级 → `错误处理`
3. 生成片段（描述 + 符号 + 位置），**分批 `ki_bulk_sync_relation` 写入（每批 ≤5 条）**，写完刷新索引（§2.3）
4. **不记录**：简单 getter / setter、组件模板（走知识库）、一次性临时代码、纯配置值

**与代码知识库的边界**

| | 片段记忆 | `ki-search`（`${scope}`） |
|---|---|---|
| 内容 | 代码级要点（函数、流程、数据模型） | 架构知识、模块职责、API 设计 |
| 粒度 | 函数 / 方法 / 核心流程 | 模块 / 系统 |
| 存储 | `${scope}-memory`（按内容归类） | `${scope}`（只读） |
| 读法 | 语义检索 + 直接取原文 | 语义检索优先（四步走） |

> **写代码前先查**：动手实现工具函数 / 核心流程之前，先按 `ki-search` 四步走确认片段记忆里没有可复用的——重复造轮子比"不写记忆"更亏。

### 2.7 会话收尾自查（运行期约定，非初始化动作）

> **触发点**：用户说"好 / OK / 可以"（确认结果）、"记录到文档 / 保存"、"开始实施 / 开始写代码"、"下一个 / 继续"（切话题），或对话自然转折。**不是等用户说"结束"才做。**

```
□ 有未记录的新需求？            → AGENTS.md「近期工作」一行
□ 有未记录的代码要点 / 决策？    → ${scope}-memory（§2.5 / §2.6）
□ 发现过时 / 描述错误的文档？    → 当场修正或删除并留痕（§2.8）
□ 有"发现了但没做"的事？        → use_skill("event-report")
□ 产出了产物文档（报告 / 复盘）？→ 挂到对应事件（docs，先挂再推终态，见 event-report §5）
□ 做完的事对应未收口事件？      → ki_event_edit(action=stage) 推到真实阶段（已修复不许停在「修复中」）
□ 进度有变化？                  → 更新「近期工作」对应条目
□ 索引有变更？                  → 刷新「项目记忆索引」（§2.3）
□ 本次有写工具返回 url？        → 收尾逐条贴 `[文档名称](url)`（§2.7.1 ⑤）
□ 近期工作 > 7 天或 > 20 条？   → 立即归档（§5 T1，强制）
```

### 2.7.1 收尾汇报格式（给用户看的那段「收尾」）

> **与 §2.7 的分工**：§2.7 是**自省表**（内部逐项核对，不必逐条展示）；本节是**输出格式**（展示给用户）。先自查，再按本节汇报。
> 本节是「收尾汇报」的**格式真源**，AGENTS.md 置顶「第四原则」（§2.1 ⑬ / §2.2 ⑩）与模板只保留四要素 + 条件要素摘要。

**触发**：给出交付结论前、多阶段任务的每个阶段结束、用户说"好 / 可以 / 下一个"。

**固定四要素 + 一个条件要素**，各一行 bullet，整段标题用 `收尾`：

| # | 要素 | 写什么 | 不写什么 |
|---|---|---|---|
| ① | **状态变更** | 事件阶段流转（`📮 #N → 已关闭`，沿用 `event-report` §10 回执格式）、关键文件 / 端点 / 测试结果、**是否已提交** | 逐文件 diff、完整命令输出、代码片段 |
| ② | **沉淀落点** | 写进哪个库 / Group / Relation（`${scope}-memory → 决策记录/…`）、AGENTS.md「近期工作」记了哪一行 | 记忆正文原文（要看自己查） |
| ③ | **剩余边界** | 已知限制、未覆盖的测试、待复核项、被推翻的旧判断；**没做的写"未做"** | 与本任务无关的既有问题（另报事件，见 `event-report`） |
| ④ | **待你决定** | 需用户拍板的：是否提交、是否 breaking、要不要推到终态 | 自己能决定的小事 |
| ⑤ | **文档链接**（条件要素） | 本轮用 MCP 写工具（当前是 `ki_sync_relation` / `ki_bulk_sync_relation` / `ki_edit_relation`；**未来任何返回 `url` 的写工具同样适用**）**成功**新增或修改了文档、且返回体里带 `url` 时，在回复末尾逐条 `[文档名称](url)`；名称取返回的 `relation`（文档名），多条各占一行 | 拿不到 `url` 时**不写、不自己拼地址**；失败 / 被跳过的文档不列；同一文档**跨轮次**不重复贴 |

**硬性口径**：

- **只写已发生的**：事件真的推了、记忆真的写了才进 ①②；计划做但没做的写进 ③
- **为空写「无」**：①~④ 不省略要素，也不编内容凑格式
- **⑤ 是条件要素**：没有链接就**整条不出现**（不写「无」占位）；有则**必须贴**（用户明确要求：写到对话末尾，Markdown 链接格式 `[文档名称](url)`）
- **时间窗 = 链接首次出现的那次回复**：本轮写入就在本轮收尾列出；**同一对话里已贴过的链接不再重复贴**（否则长对话每轮刷屏），只有出现新写入时才新增条目
- **一次回复内允许出现两次**：正文里提过、收尾块再列一次（末尾这次是给复制用的），不算「重复贴」——「不重复贴」指的是**跨轮次**
- **批量 > 5 篇时收敛**：列前 5 条 + 一行「……共 N 篇（其余可在浏览页该分组下查看）」，不逐条刷 20 行
- **没有收尾块时**（如一句确认的简短回复）：链接单独放回复最后一行，仍是 `[文档名称](url)`
- **长度 ≤ 6 行**：用户没问的细节不展开，需要时再补一两句（⑤ 的多条链接不计入这 6 行）
- **不复述正文**：前面详细说过的结论只留一句指位
- **只写一行结论的豁免条件（同时满足才算）**：改动 ≤1 个文件 **且** 无事件流转、无新沉淀、无待决事项 **且** 无 ⑤；其余一律四要素齐全——**"我觉得任务小"不构成豁免**（历史教训：可跳过的软条件必然被跳过）

**示例**：

```
收尾
- ① #46 已关闭（visibility full）；改了 2 个文件，测试 20/16 全绿；未提交
- ② 沉淀 kisearch-memory → 决策记录/AI 查找/删除旧执行器时的能力搬迁清单；AGENTS.md「近期工作」已记一行
- ③ 边界：tool-runner 对越界 scope 是回落到 targets[0] 而非回错给模型，目前无测试覆盖
- ④ 待你定：是否提交
- ⑤ 文档：[取址与落点事实](http://127.0.0.1:7423/browse?scope=kisearch-memory&group=接口信息%2F关系与索引管理&relation=MCP%E5%86%99%E5%B7%A5%E5%85%B7%E8%BF%94%E5%9B%9E%E6%96%87%E6%A1%A3%E9%93%BE%E6%8E%A5%E7%9A%84%E5%8F%96%E5%9D%80%E4%B8%8E%E8%90%BD%E7%82%B9%E4%BA%8B%E5%AE%9E)
```

### 2.8 文档健康维护：过时与描述错误的文档主动修正或删除（运行期约定，非初始化动作）

> **与 §2.5 的分工**：§2.5 管"该写什么"；本节管"**已经写下的不对了怎么办**"。写完就不管，等于把错误知识长期留在检索第一线，比不写更糟。
> **硬性口径：发现即处理，不问"要不要改"。** 只有影响面大的判断（是否推翻既有决策、是否删掉别人还在用的东西）才问用户。
> **生效前提**：AGENTS.md 的「第二原则」必须含"文档健康行"（§2.1 ⑩ 初始化写入 / §2.2 ⑦ 增量补齐）。老项目没跑过增量更新的，先重跑一次——否则本条只活在 skill 里，运行期无人提醒。

**什么算「过时 / 描述错误」**（任一命中即算）：

| 信号 | 例子 |
|---|---|
| 与代码 / 现网不符 | 签名、参数、默认值已改；接口路径 / 错误码已废弃；模块改名或拆并 |
| 与现行决策冲突 | 方案已被推翻、约定已换（按"改 + 留一句旧结论"处理，**不直接删**） |
| 自相矛盾或重复 | 同一主题两种说法；同一关系在多处重复且开始漂移 |
| 已彻底失效 | 指向的路径 / 链接 / 命令不存在；系统已下线、流程已废止 |
| 结构错位 | 落组语义不符；索引里出现不存在的组（后者由 §2.2 ③ 机械处理） |

**处理顺序：先改，后删；删只删"无用"，不删"历史"**

1. **能改就改（默认）**：局部偏差 → `ki_edit_relation`（改几行）；整篇过期 → `ki_sync_relation` 覆盖（写前必 `ki_get_module_info` 取回正文，整篇覆盖无追加语义）。AGENTS.md 的缓存类内容（索引 / 团队约定）以 ki 为权威回刷。**只有几段失效**时不必删：改那几段，或在正文首行加一行「⚠️ 已废弃，见 {新文档}」，让检索命中时就看得见。
2. **该删才删**（三条同时满足）：① **已读全文**确认（`ki_get_module_info`，不凭标题、不凭印象）② 无独有信息（价值已合并到别处，或彻底失效）③ 删掉不会让引用断链（**先查事件 `docs` / `refs` 是否挂载该文档（`ki_event_list` + `ki_event_get`），再查别处正文是否引用它**）。工具 `ki_delete_relation`（进回收站、可恢复，但恢复后索引重建需要数秒；有未收口的 `ki_edit_relation` 草稿时会被拒，先 cancel / finish）。
3. **历史不删，只治失效**：被推翻的判断按 §5 改正文并保留一句"原判断是 X，因 Y 改为 Z"；**同一主题被新版本取代**时，删掉旧版本或在两处互标"已被 X 取代"（同一仓内保持一致），别让两份都像现行版本。删的永远是**会误导检索的失效内容**，不是**演进史**。
4. **删除要留痕并刷新索引**：按 §2.3 重刷「项目记忆索引」（含 `文档` 段的组要更新折叠篇数与篇名）；收尾汇报 ① 里写清删了哪个 Group / Relation、为什么，不静默清理（§2.7.1）。

**对象分层**

| 对象 | 改 | 删 |
|---|---|---|
| AGENTS.md 自身（索引 / 团队约定 / 近期工作） | 以 ki 为权威回刷（§2.2 ③ / §3.6） | 索引条目：ki 已无 → 删；其余按 §5 归档，不直接删 |
| `${scope}-memory` 记忆与文档 | `ki_edit_relation` / `ki_sync_relation` 覆盖 | `ki_delete_relation`（进回收站） |
| 项目内文档（README / docs / skill 说明） | 当场同步（参数、命令、示例、失效链接） | 被取代 / 合并后**确认无用**才删；文件删除走项目提交口径 |
| `${scope}` 代码知识库 | **先取得用户明确授权**（§2.5 六 / 🔴 33） | 同上，未授权不删 |

**与事件的分工**：当前任务范围内、顺手能改能删 → **直接做**；跨模块、需要取舍、删了要别人知情 → `use_skill("event-report")` 上报，**不擅自删**。判据仍是"要不要有人跟到收口"。

**禁止**：只在对话里说一句"这里过时了"就翻篇；为"看起来干净"批量清记忆；删未授权的代码知识库或别人还在用的团队约定。

模板章节结构：

```
# AGENTS.md - AI AGENT 项目记忆文件

├── 🔒 安全底线（置顶说明块） # 本文件与一切代码/测试禁止写入敏感信息（私钥、线上地址、真实 IP、账号口令、个人信息），示例用占位符

├── 项目记忆索引      # ki ${scope}-memory scope（Group 结构 + 热门 Relation），机械转写
├── 团队约定          # 同步 ki ${scope}-memory「团队约定」Group（缓存，空则写"无"）
├── 知识文档入库      # 运行期约定（什么该传 / 传哪个 Group / 上传后验证），初始化只写约定不上传
├── 用户画像          # 直接存储，不走 ki（维度按需新增，不预置空维度）
├── 近期工作 (7天内)  # 直接存储，不走 ki；每条 1 行；超 7 天压缩进「历史工作记录」
├── 历史工作记录      # 归档区（原计划的外部 archive.md 已废弃，规则见 §5）
└── 更新日志          # 仅记结构性变更，最近 10 条
```

> 代码知识库（`${scope}`）索引不写入 AGENTS.md。
> **为什么归档留在本文件内**：外部 `archive.md` 在实践中从未被创建（实测某项目「近期工作」积累到 742 行 / 224 条、横跨 3 个月，`archive.md` 不存在，反而在 AGENTS.md 内部自发生长出「历史工作记录」章节）。同文件归档少一次文件跳转、可直接检索，故定为正式口径。

## 3.5 直接存储章节维护（用户画像 + 近期工作）

> **用户画像与近期工作均不再使用 ki scope/Group，直接存储在 AGENTS.md 对应章节。**

### 用户画像

#### 维度（按需新增，不预置空维度）

```
常见维度：沟通偏好 / 工作习惯 / 代码风格 / 工具链 / 技术背景
```

#### 写入规则

- 对话中发现用户偏好 → 直接更新 AGENTS.md 对应小节（覆盖写入）
- 维度缺失 → 新增小节（命名保持 4-8 字名词短语）
- **不硬造内容**：模板只给格式，不预置 6 个空小节的占位文字；没有偏好就只留已观察到的 1-2 个维度
- **只记偏好，不记个人信息**：真实姓名、手机号、邮箱、身份证、住址、公司内部人名一律不写（见 §8 禁忌 16），必要时代称（如"项目负责人"）
- **不执行任何 ki MCP 调用**

#### 读取规则

- 对话开始 → 读取 AGENTS.md"用户画像"章节，加载用户偏好
- 无需任何 ki 查询

### 近期工作

#### 写入规则

- 格式：**单小节、单列表**，每条**严格 1 行**：`- [YYYY-MM-DD] {一句话：做了什么 / 结论是什么}`（≤ 80 字）
- **详情不进 AGENTS.md**：根因、代码位置、验证数据、审查结论 → 写入 `${scope}-memory`（`ki_sync_relation`）或项目 `.plans/` / `.debug/` 台账，AGENTS.md 只留一行结论 + 指向（如 `详见 .debug/xxx/`）
- 状态标记：进行中 `🔄`、已完成 `✅`、待拍板 `🆕`
- **写入前脱敏**：线上域名 / 真实 IP / 账号口令 / Token / 个人信息一律替换为占位符或去掉（如"线上环境"、"`<HOST>`"），见 §8 禁忌 16
- 容量：本章节**目标 ≤ 20 条 / ≤ 40 行**，超过即触发归档（见下）
- **不执行任何 ki MCP 调用**（无"最近需求"/"进度" Group）

> **为什么强制 1 行**：实测某项目该章节 224 条、742 行（占 AGENTS.md 73.5%），而 AGENTS.md 是每次对话全量注入的上下文——流水账详情会把"缓存索引"的成本变成负债。规格与现实的偏差是数量级的，故此处收紧为硬约束。

#### 过期清理（归档）

- 已完成 / 待拍板条目超过 7 天 → 压缩为一行后移入本文件「历史工作记录」章节（按日期倒序追加）
- **进行中 `🔄` 条目永久保留**，不归档
- 归档时保留"结论 + 仍有效的决策"，删除实现细节与验证清单（细节查 git 历史或台账）
- 本文件内归档，**不再创建 `archive.md`**（口径已收敛）

## 3.6 团队约定章节同步（AGENTS.md ↔ ki）

> **同步源**：`${scope}-memory` → 「团队约定」Group。本节是缓存，权威数据在 ki。
> **目的**：agent 读 AGENTS.md 即可直接获取团队约定，免一次 ki 查询。

### 同步规则

- **方向**：先写 ki（`ki_sync_relation(scope: "${scope}-memory", group: "团队约定", relation, module_info)`），再把要点回刷本节。**禁止只在 AGENTS.md 写约定而不写回 ki。**

- **刷新时机**：完整初始化（§2.1 ⑤）、增量更新（§2.2 ③）、写入/修改团队约定后。
- **同步日期**：每次回刷时更新本节引用块中的 `同步日期: YYYY-MM-DD`。

### 读取规则

- 对话需遵循团队约定时先读本节；需完整原文再走 `ki_get_module_info(scope: "${scope}-memory", group: "团队约定", relation)`。

```markdown
## 项目记忆索引
```

## 5. 近期工作维护与归档

> **近期工作直接存储于 AGENTS.md，不从 ki 提取；归档也留在本文件（「历史工作记录」章节），不再使用外部 `archive.md`。**
> 本节是该口径的唯一真源（原 `rules/ai-codekb-memory.md`「归档机制」已并入本节，2026-11-19）。

### 写入（格式）

- 单小节单列表，每条一行：`- [YYYY-MM-DD] 🔄|✅|🆕 {一句话结论}`（≤ 80 字）
- 详情（根因 / 文件位置 / 验证数据 / 审查结论）写入 `${scope}-memory` 或项目台账（`.plans/`、`.debug/`），此处只留指向

### 归档触发（任一命中即执行）

| # | 触发条件 | 动作 |
|---|---------|------|
| T1 | **刚往「近期工作」追加了新条目** | 追加后立即数条目数：> 20 条 → **本次就归档**，不留到下次 |
| T2 | 条目日期 > 7 天且状态非 `🔄` | 压缩为一行后移入「历史工作记录」 |
| T3 | 本章节 > 20 条或 > 40 行 | 全量整理一次：按上述规则归档 |
| T4 | 完整初始化 / 增量更新（§2.1 / §2.2） | 顺带检查 T2、T3 |

> **为什么把 T1 放在第一位**：旧规则只有"访问本章节时检查归档"，而"访问"是可跳过的动作——实测某项目因此积累到 224 条 / 742 行，规则形同不存在。**"写入"是必然发生的事件**，把检查点绑到写入后，才不依赖 AI 记得回头自查。
> 配套：§2.7 会话收尾自查同样保留这一项，两处互为兜底。

### 压缩规则

**前置校验（含多行详情时不可跳过）**：条目若带子列表/多行详情，压缩前必须确认详情**已落到** `${scope}-memory`（`ki_sync_relation`）或项目台账（`.plans/`、`.debug/`）；**没落地就先写，再压缩** —— 否则压缩等于删除信息。本来就只有一行的条目直接搬，无需额外落地。

```
保留：结论（做成了什么 / 决定了什么）、仍有效的约束、被推翻的旧判断（一句话）
删除：实现步骤、验证清单、审查过程、失败尝试的中间状态（这些去 git 历史 / 台账查）
```

目标：归档条目每条 ≤ 120 字，按日期倒序追加，不删除历史。

### 存量迁移（首次套用本规则时）

当已存在历史堆积（如数百行、跨数月）时，一次性整理：

1. 按日期分组，`🔄` 的留在「近期工作」
2. 其余逐条压缩为一行，按倒序写入「历史工作记录」
3. 压缩时保留「结论 + 决策」，细节不搬运
4. 整理后在更新日志记一条结构性变更

### 其他数据的归档口径

| 数据 | 位置 | 规则 |
|---|---|---|
| 「当前状态」Relation | ki `${scope}-memory` | 超 30 天视为过期，**在 ki 内压缩**为一条摘要（`ki_sync_relation` 覆盖写回），不搬到 AGENTS.md |
| 其他 Group（含代码片段） | ki `${scope}-memory` | 永久保留，不归档 |

> **归档不删除历史**：AGENTS.md 条目移入「历史工作记录」，ki 条目在库内压缩，两边都不允许直接删。

## 6. 更新日志维护

> **只记结构性变更**，不记日常条目增删（那些在「近期工作」里已有，重复记录会把两处都撑大）。


保留最近 10 条，超出删除最早的。

## 7. 协同

- **与 alwaysApply 规则 / AGENTS.md 置顶章节**：本 skill **不常驻**（用户手动触发才加载），而「主动沉淀 / 上报 / 预取 / 收尾汇报」要求每次对话都在场——常驻那层由用户级规则与 AGENTS.md 的「第一 ~ 四原则」章节承载（§2.1 ⑧~⑬、§2.2 ⑦~⑩）；**行为口径的真源在本 skill**（§2.5 / §2.6 / §2.7 / §2.7.1 / §5），置顶章节只保留触发约定与指针。历史上"规则文件 + skill + AGENTS.md"三处各写一份「近期工作格式」，结果与真实产物互不一致——**AGENTS.md 格式的唯一真源是 `AGENTS-template.md`**，其余一律只引用不重定义。
- **与 `ki-search` 规则**：AGENTS.md 索引只缓存 `${scope}-memory`；检索走 `ki-search`，**默认优先 `${scope}-memory`**（`${scope}` 仅作宏观兜底，与 `ki-search` 规则禁忌 10 一致），确认主题在代码库时再查 `${scope}`；两者都确需时才一次传两个 scope（`ki_search(scope: "${scope},${scope}-memory", query)`）。模板顶部须写明这条约定，**不得写成"永远同时查两个 scope"**——那会与 `ki-search` 的"优先 memory"口径打架。
- **与 `ki-upload` skill**：本 skill 定义**判断层**（什么文档该入库、落哪个 Group、怎么验证、怎么回填，见 §2.4）；`ki-upload` 提供**执行层**（`use_skill("ki-upload")` → `upload` / `upload-dir` / `events` / `ping` / `status`，含参数、错误码、httpflex 踩坑；`events` 用于上传前确认事件状态）。**分工边界**：本 skill 不重写上传参数与错误码，`ki-upload` 不负责 AGENTS.md 结构与 Group 归类。初始化**不触发上传**；缺上传能力时降级为打印命令（§2.4 五），**不阻塞初始化**。**运行期同一条通道也服务主动沉淀**：本地已写好的成篇文档（几百行 / 500+ 行）直接 `use_skill("ki-upload")` 上传，不要塞进 relation（§2.5 四）。
- **与 `task-recall` skill**：本 skill 把「先取文档」写进 AGENTS.md **第一原则（第一动作，§2.1 ⑧）**与**第三原则（执行细则，§2.1 ⑫ / §2.2 ⑨）**及模板；**判据与用法（何时调、画像四要素、怎么消费 `nextActions`/`needMore`/`skipped`、禁忌清单）以 `task-recall` 为准**，本 skill 不复制其内容。第三原则写入前必须先做 `ki_recall` 能力探测，工具不存在则不写（**第一原则照写，只降级措辞为"跳过预取、直接 ki_search"**）。
- **与 `event-report` skill**：本 skill 负责把**上报触发约定**写进 AGENTS.md（第二原则，§2.1 ⑩ / §2.2 ⑦）与模板；`event-report` 提供**执行层**（分流判据、三道门、字段模板、去重、文档三分法、收口与召回、降级）。**判据真源在 `event-report`**，本 skill 与 AGENTS.md 只留一句指针，**禁止各写一份分流表**。初始化**不触发任何上报**。
