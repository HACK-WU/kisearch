# agents-md-init AGENTS.md 初始化

> **前置条件**：AI 已了解 ki MCP 工具。AGENTS.md 位于项目根目录。
> **格式模板**：完整 AGENTS.md 模板见 [AGENTS-template.md](AGENTS-template.md)，本文件不内嵌模板。
> **边界**：本 skill 只负责"结构与索引建对"（用户手动触发，**禁止 AI 自动触发**）；日常条目追加、7 天归档、**运行期把信息/决策主动写进 ki** 由 `ai-codekb-memory` 规则（alwaysApply）执行（见 §7）；本 skill 只把「主动沉淀」这条约定写进 AGENTS.md（§2.5 / §2.1 ⑩）。

---

## 1. 概述

**目的**：维护 AGENTS.md 的**结构与索引缓存**，确保索引信息与实际 ki 数据保持一致；并把「主动沉淀」（§2.5）与「知识文档入库」（§2.4）两条**运行期约定**写进文件，让它们在每次对话的上下文里都在场。本 skill 只管"把结构建对"（手动触发）；日常条目追加、运行期写入与 7 天归档由 `ai-codekb-memory` 规则（alwaysApply）负责。历史上为解决"规则文件内嵌模板导致内容混乱"而独立成 skill。

**功能**：
- 用户手动触发时创建/重建 AGENTS.md 的结构（如用户说"初始化 AGENTS.md"、"刷新索引缓存"）
- 判定目标项目记忆 scope（`${scope}-memory`），多候选时不擅自全量写入（见 §2.0）
- 查询 ki 获取真实索引数据填充项目记忆索引，**以 `ki_group_list` 输出为权威机械转写**（见 §2.3）
- Group 骨架按需补建，其余交由 `ki_sync_relation` 自动补建（不必逐个预建，见 §2.1）
- 同步「团队约定」Group 内容到 AGENTS.md"团队约定"章节（空则写"无"，见 §3.6）
- 代码知识库（`${scope}`）索引不写入 AGENTS.md，查询走 `ki-search` 直连 ki
- 用户画像与近期工作章节的**结构**在此建立；条目增删与 7 天归档由 `ai-codekb-memory` 规则维护
- **置顶写入「第一原则：遇事不决，ki-search」**——提醒 AI 遇事先用 `ki_search` MCP 工具查项目记忆，不凭记忆猜；并提示「跨库检索前先 `ki_view_list` 看视图」（视图会变，**不缓存列表**、每次实时查，见 §2.1 ⑧ / §8 禁忌 23）
- **置顶写入「安全底线：代码与测试禁止敏感信息」**——私钥、线上地址、真实 IP、账号口令、个人信息一律用占位符（见 §2.1 ⑨ / §8 禁忌 16）
- **置顶写入「第二原则：主动沉淀，不等提示」**——开发 / 设计 / 排查过程中产生的信息、决策、设计，AI **自己**写进 `${scope}-memory`，**用户开口不是触发条件**（见 §2.5 / §2.1 ⑩）
- **定义「主动沉淀」约定**：什么该沉、落哪个 Group、粒度与查重、**通道选择（短内容走 `ki_sync_relation`，本地成篇文档走 `use_skill("ki-upload")`）**、写完怎么验证、什么不该沉（见 §2.5）；写入工具参数与片段格式由 `rules/ai-codekb-memory.md` 负责，本 skill 不重定义（见 §7）
- **`ki` CLI / MCP 工具行为异常必须当场汇报**，不静默重试、不自愈式绕过（见 §1.6 / §8 禁忌 17）
- **定义「知识文档入库」约定**：哪些产出的文档该上传进 `${scope}-memory`、落哪个 Group、怎么验证、怎么回填（见 §2.4）；实际传输能力由 `use_skill("ki-upload")` 提供，本 skill 不重写其参数与错误码（见 §7）
- 无真实数据时用示例格式兜底（标注 ⚠️）

**使用场景**（用户手动触发）：
- 首次对话，用户要求初始化 AGENTS.md
- 索引变更后用户要求刷新缓存
- 手动触发"初始化 AGENTS.md"、"刷新缓存"
- ki 中无任何 scope 时引导用户创建
- **开发 / 设计 / 排查过程产出了可复用文档**（设计文档、排查结论、调研报告、上线手册），需要沉淀成可检索的项目记忆 → 按 §2.4 走 `use_skill("ki-upload")` 入库
- 用户说"这份设计文档入库 / 传到 ki / 沉淀一下" → 先按 §2.4 判定该不该传、传哪个 Group，再执行上传
- 用户说"以后决策/设计自己记进 ki，别等我提醒" → 按 §2.5 口径把「第二原则：主动沉淀」补进 AGENTS.md（写入动作同 §2.1 ⑩ / §2.2 ⑦，不必改 skill 本体）

## 1.5 首次使用引导

> **当 `ki_scope_list` 返回空列表时，AI 应主动引导。**

```
① ki_scope_list → 无任何 scope（或本项目尚无 memory scope）
    ↓
② 主动提示用户：
    "检测到项目尚未配置 ki 索引。是否需要我帮你初始化？"
    ↓ 用户确认
③ 确定 memory scope 名称（默认 `${项目目录名小写}-memory`，判定口径见 §2.0）
④ ki_group_create(scope: "<memory scope>", path: "背景与目标")
    # scope 不存在时该工具会自动创建并返回 createdScope，无需单独建 scope
    # 其余 Group 不必逐个预建：ki_sync_relation / ki_bulk_sync_relation 会按写入路径自动补建
⑤ 执行完整初始化（步骤 2.1）
```

> 用户拒绝则跳过，后续按需触发。
> 用户画像与近期工作不创建对应 scope/Group——直接写入 AGENTS.md 的"用户画像"/"近期工作"章节。
> **不要给代码知识库（`${scope}`）建「项目概述」等组**：代码库索引不写入 AGENTS.md，本 skill 也不维护它，建出来只会是空壳（历史实证：某项目 scope 仅剩一个 wikiCount 0 的「项目概述」空组）。

### 异常处理

若本 skill 文件不可用（如新克隆项目）：跳过 AGENTS.md 初始化，后续用户明确要求时再按需处理（kisearch 缺失由 `ai-codekb-memory` 规则提示安装）。

## 1.6 ki 工具异常上报（必做）

> 本 skill 全程依赖 `ki` CLI 与 MCP 工具。**它们报错、或"跑通了但不像应该的样子"时，当场向用户汇报，不得静默重试或换路绕过。**

**触发条件**（任一命中即算异常，不以"最终能跑完"为标准）：

| 类型 | 例子 |
|------|------|
| 失败 | 报错、非零退出、超时/挂起；**即使重试后成功，首次失败也要说** |
| 结果不符 | 写入成功但 `ki_group_list` 查不到；`ki_search` 返回条数与 `limit` 不一致；scope / Group / Relation 名被改写；字段缺失或类型不对 |
| 违背承诺 | 与工具描述或本 skill 口径矛盾：该自动补建 Group 的没补、多级路径父组未校验、所谓幂等写入却重复叠加 |
| 静默降级 | 该失败却返回空列表 / `- 暂无`；部分成功却报全成功；被截断/被收敛无任何提示 |
| 输出污染 | 进度条、日志混进 stdout 破坏可解析输出；编码/换行错乱 |

**汇报格式**（一次给全，不要挤牙膏）：

- 工具与命令：`ki_xxx(...)` / `ki <子命令>`
- 入参：完整参数（含 scope / group / limit，敏感值脱敏）
- 实际：原始输出关键行 或 退出码
- 预期：按工具描述、`docs/cli.md` 或本 skill 应有行为
- 影响：本次流程哪一步不可信、是否已阻塞、是否影响已写入的索引
- 已试：重试次数与结果、是否已绕过（默认不绕过）

**禁止**：

- 静默重试把异常掩盖成"正常"；只在收尾时飘一句"中途有报错但已解决"
- 改参数 / 换工具 / 手改文件绕过异常后把流程跑完，不告知用户
- 把可疑输出当权威数据**机械转写**进 AGENTS.md（宁可停下等结论，不写入不确定的索引，见 §2.3）

## 2. 初始化流程

> **仅当用户明确说明要初始化或刷新 AGENTS.md 时才执行，禁止 AI 自动触发。**

### 2.0 目标 memory scope 判定（必做）

> **背景**：`ki_scope_list` 返回的是本机全部 scope（实测同一台机器可有 100+ 个，其中多个 `*-memory` 并存）。**"对每个 `${scope}-memory` 都写一节"是错的** —— 会把历史测试 scope 与其他项目的项目记忆写进本项目的 AGENTS.md。

**判定顺序**（命中即停）：

```
① AGENTS.md 已存在且"项目记忆索引"章节已记录 memory scope 名？
    ├─ 是，且 ki_scope_list 里仍有该 scope → 直接沿用（缓存自证，不重新推断）
    └─ 是，但 ki 里已不存在（被删/改名）→ 回到 ② 重新判定，并告知用户"原记录的 X 已不存在"
② 只有一个 scope 带 -memory 后缀？
    └─ 是 → 用它
③ 多个候选 → 依次过滤：
    ├─ 保留 registered: true 的（在配置中正式注册）
    ├─ 保留与项目目录名 / git 仓库名有词根重合的（如目录 xpert ↔ scope xpert-memory）
    └─ 仍剩多个 → 问用户一次："本项目项目记忆用哪个 scope？候选：A / B"，不猜
④ 判定结果写入 AGENTS.md 索引章节首行（`数据来源：ki 的 <scope> scope`），供下次会话直接沿用
```

**边界**：只在"初始化 / 重建"时判定；日常增量维护（`ai-codekb-memory` 规则）沿用 AGENTS.md 已记录的值，不重新判定。

**路由**（均需用户明确要求，禁止 AI 自动触发）：

```
用户明确要求后
    │
    ├── AGENTS.md 不存在？
    │       └── 是 → 执行完整初始化（步骤 2.1）
    │
    ├── AGENTS.md 存在但无"项目记忆索引"章节？
    │       └── 是 → 执行完整初始化
    │
    └── AGENTS.md 存在且完整？
            └── 检查索引一致性 → 不一致则增量更新
```

### 2.1 完整初始化

```
① 判定目标 memory scope（§2.0）→ 得到唯一 scope
② ki_group_list(scope: <目标>, mode: "full", depth: 4)
     → Group 结构（权威源，含各层子组）
③ ki_group_list(scope: <目标>, mode: "hot", hot_count: 3)
     → 热门 Relation（Top 3）
④ Group 骨架补建：只补本 skill 需要立即展示的最小集
     - 「团队约定」必建（§3.6 依赖它做同步源）
     - 其余按模板清单与 ② 的差集补，且只补"首层必要项"；不必一次建满 12~18 个
     - 工具：ki_group_create(scope, path)；parent 必须已存在，多级路径先建父
⑤ 同步「团队约定」Group → 填充 AGENTS.md"团队约定"章节（Group 为空则写"无"，见 §3.6）
⑥ 用户画像与近期工作章节 → 建立章节骨架（空模板，预置维度按需，不硬造内容）
⑦ 写入 AGENTS.md（参考 AGENTS-template.md）：
     ② ③ 的输出**机械转写**进"项目记忆索引"，禁止自由摘要（见 §2.3）
⑧ 核对置顶「第一原则」：AGENTS.md 标题下第一个章节必须是
     「## 🔑 第一原则：遇事不决，ki-search」，正文含 ① 查询顺序 ② **跨库检索前先 `ki_view_list` 看视图**
     ③ 视图只读不可写入；缺失即补；**这是初始化必做项，不是可选项**
⑨ 核对置顶「安全底线」：文件头部说明块必须含一句
     "**本文件与一切代码、测试禁止写入敏感信息**（私钥/证书、线上地址、真实 IP、
      账号口令/Token、个人信息），示例一律用占位符"，缺失即补；**同为初始化必做项**
⑩ 写入「主动沉淀」章节（运行期约定，见 §2.5），位置**紧随「第一原则」之后**
     · 标题固定 `## 📝 第二原则：主动沉淀，不等提示`
     · 只写约定（何时沉 / 落哪个 Group / 写前查重 / **两条通道：MCP 与 `ki-upload`** /
       写后验证 / 不写什么），**初始化阶段不写任何记忆内容**
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写
⑪ 写入「知识文档入库」章节骨架（运行期约定，见 §2.4）
     · 只写约定，**初始化阶段不扫描、不上传任何文档**
     · 章节内容照 AGENTS-template.md 该节抄，不自行扩写
```

> **⑩ ⑪ 的存在理由**：AGENTS.md 是每次对话全量注入的上下文，运行期 AI 读得到这些约定才会照着做；只写在 skill 里（用户手动触发才加载）等于没人看得见 —— 「主动沉淀」尤其如此：**没人在上下文里提醒，AI 就会等用户开口才记**。

> 代码知识库 `${scope}` 的索引不初始化到 AGENTS.md，仅缓存 `${scope}-memory` 项目记忆索引。
> **不预建空 Group**：`ki_sync_relation` / `ki_bulk_sync_relation` 写入时都会**自动补建缺失的 Group 树**（多级路径的父组一并创建），写入后自然成形；而 `ki_group_create` 只能单个建、没有批量工具，预建 12+ 个组是纯调用成本。

### 2.2 增量更新

当 AGENTS.md 已存在但部分过期时：

```
① 读取 AGENTS.md，取其中已记录的 memory scope 名（§2.0 ①，不再重新推断）
② ki_scope_list → 确认该 scope 仍存在（不存在 → 提示用户，不静默改写）
③ 漂移自检（本次核心）：以 ki 为权威，与文件逐项比对
   - Group 结构：ki_group_list(mode: "full") 的每个组/子组 ↔ 索引章节的列表项
       · ki 有、文件无 → 补
       · 文件有、ki 无 → 删（组已被删除）
   - 热门 Relation：mode: "hot" 的结果 ↔ "热门 Relation" 小节
   - 团队约定：ki_group_list(groups: "团队约定", mode: "full") ↔ "团队约定"章节
④ 检查"近期工作"时间戳与条目数（> 7 天 / 超过 ~20 条 → 触发归档，规则见 §5）
⑤ 用户画像：保留已有内容，仅当出现新维度时补充小节
⑥ 核对置顶「第一原则」与「安全底线」是否存在（同 §2.1 ⑧ ⑨，缺失即补；老文件普遍缺这两条，且第一原则多缺视图提示）
⑦ 核对「第二原则：主动沉淀」章节是否存在（同 §2.1 ⑩；老文件普遍没有，缺失即补，
   **只补约定不补记忆内容**；已有但缺"不等用户提示"这条硬话的，补齐）
⑧ 核对「知识文档入库」章节是否存在（同 §2.1 ⑪；老文件普遍没有，缺失即补，**只补约定不补上传**）
⑨ 结构性变更写入"更新日志"（仅结构变更，见 §6）
```

> **③ 的方法论**：比对必须"机械"——把 `ki_group_list` 的树输出逐行映射成列表项，而不是读完凭印象重写。历史实证：某项目初始化后新增了 2 个组（错误库、决策记录）和 1 个子组，靠印象摘要的索引连续数周未发现缺失，同期"热门 Relation"一直写着"暂无"而实际已有 3 条热区数据。

### 2.3 机械转写规则（防漂移）

| 数据源 | 转写方式 | 禁止 |
|--------|---------|------|
| `ki_group_list(mode: "full")` | 树形缩进逐层映射为嵌套列表，组名原样照抄 | 合并同类组、省略"看起来空"的组、改写成业务名称 |
| `ki_group_list(mode: "hot")` | 每条一行：`- {Group}/{Relation} (score: {n})` | 无数据时编造；空热区写 `- 暂无` 并注明日期 |
| `ki_group_list(groups: "团队约定")` | 每条压成一行要点 `- {Relation}: {一句话}` | 全文转储；空组留空（必须写 `- 无`） |

> 索引章节首行固定写 `> 数据来源：ki 的 <scope> scope（YYYY-MM-DD 初始化）`，供下次会话判定目标 scope 与判断缓存新旧。

**折叠条款（唯一例外，判据机械）**：组路径中**含独立 `文档` 段**（如 `错误库/文档`、`错误库/文档/sub`）的组是 `ki-upload` 批量导入的文档（§2.4 约定）。这类组折叠成一行且**附前 3 篇篇名**（保住可发现性），形如 `- 错误库/文档（12 篇：OOM 排查、端口冲突、依赖装不上…）`，不逐条展开 relation。

> **为什么必须折叠**：一篇文档 = 1 个 relation，几十篇就是几十行；AGENTS.md 是**每次对话全量注入**的上下文，索引撑大会把"缓存"变成负债。
> **边界**：判据只有一个——**组路径里有独立的 `文档` 段**（段级匹配，`文档规范` 这类子串不算；源目录带子目录时落点延伸成 `文档/sub`，判据仍成立）。手写记忆的组不得折叠；若该 `文档` 段已被**手写** relation 占用，导入改用 `文档归档` 段并在本节写一行说明，避免手写内容被误折叠。

### 2.4 知识文档入库（运行期约定，非初始化动作）

> **初始化不扫描、不上传任何文档**。本节定义的是**运行期**该怎么做：AI 在开发 / 设计 / 排查 / 调研中产出了可复用文档，把它沉淀成 `${scope}-memory` 里可检索的记忆。
> 初始化只把这套约定写进 AGENTS.md（§2.1 ⑪）；实际传输由 `use_skill("ki-upload")` 完成（参数、错误码、脚本用法以它为准，见 §7）。
> **与 `ki-upload` 同时被触发时，scope 与 `--group` 以本节为准**——它默认按源目录推导 group，恰好不满足本节要求。

#### 一、什么时候该传（判据）

| 该传：有复用价值的结论性文档 | 不该传 |
|---|---|
| 设计文档、技术方案、API 设计 | 源码、配置、构建产物 |
| 需求报告、调研报告、模块讲解 | 临时草稿、试验片段、TODO 清单 |
| 排查结论 / 根因分析（`.debug/*/evidence.md` 的**结论部分**） | 原始日志、截图、大数据样本 |
| 上线 / 回滚 / 迁移手册 | 已过期的一次性过程记录 |

**一句话判据**：*换个会话、换个人，这份文档能不能省掉一次重复调研？* 不能就不传。

#### 二、落点与 Group

- **scope 固定 `${scope}-memory`**：与 AGENTS.md 同库，检索时一次 `ki_search` 同时命中记忆与文档
- **`--group` 必填，且路径里必须有一层叫 `文档`** —— 这是索引折叠的机械判据（见 §2.3）。留空会按源目录推导，落点不可控；源目录带子目录时会自动延伸成 `错误库/文档/sub`，判据仍成立
- 归类按文档性质（不查固定表，落到"将来谁会读到它"的那个组）：

```
设计 / 方案      → 专题记忆/{模块名}/文档
根因 / 踩坑      → 错误库/文档  或  项目踩坑点/文档
架构 / 数据流    → 项目架构/文档 或 数据流/文档
决策与取舍       → 决策记录/文档
无合适归类       → 通用记忆片段/{分类}/文档
```

> 导入（`ki import` / `ki-upload`）会自动建组，**不必先 `ki_group_create`**。

- **不要留空 `--group`**：单文件上传留空落根组 `__root__`、目录上传按子目录推导——两种都不含 `文档` 段，索引里无法归类也无法折叠

#### 三、通道选择（本机文档一律走 ki-upload）

| 情形 | 通道 |
|------|------|
| 本机文档 → 远端 ki（**默认**） | `use_skill("ki-upload")` 的 `upload` / `upload-dir`：跨机可用、自动切分 + 向量化 |
| 正文已在上下文里且很短（一段结论） | MCP `ki_sync_relation` 逐条写（**不做 chunk 切分，长文档别用**） |
| 文件与 ki 同机 | `ki import --source <dir> --scope ${scope}-memory --group <g>` |

#### 四、上传后必做两步

1. **验证**：`ki_search(scope: "${scope}-memory", query: "<文档里的一句话>")` 命中，**或至少** `ki_group_list` 能看到该 relation 名 —— **上传成功 ≠ 可检索**；`--no-vector` 时只有全文索引，别只靠语义分判断
2. **回填**：「近期工作」记一行 `- [YYYY-MM-DD] ✅ {文档/目录} 已入库 {Group}`（≤ 80 字，见 §5）

#### 五、环境不全时降级（不得阻塞）

缺 Python ≥ 3.11 / `httpflex` / `KI_URL` / `KI_TOKEN` 任一项 → **不报错、不卡住当前任务**，改为给命令：

```
⚠️ 本地缺上传能力（{缺什么}），{文档} 暂未入库。出路：
   ① use_skill("ki-upload") → 按其「前置条件」装依赖后重跑
   ② 在 ki 同机执行：ki import --source <dir> --scope ${scope}-memory --group <g>
```

> 上传过程报错（`OPEN_API_*` 码、体积超限、`VECTOR_UNAVAILABLE`）→ 按 `use_skill("ki-upload")` 的「失败处理」表定位，**不得自行改脚本参数绕过**。

#### 六、与索引的关系（影响 §2.3 转写）

**上传的每篇文档 = `${scope}-memory` 某 Group 下 1 个 relation**（文件名去 `.md`，如 `DESIGN.md` → `DESIGN`），会真实出现在 `ki_group_list` 输出里 —— 不是"看不见的附件"。所以：

- Group 路径必须含 `文档` 段，让索引能机械识别"这一组是批量导入的文档"
- 这类组在索引章节**按篇数折叠成一行**，不逐条展开（见 §2.3 折叠条款）

### 2.5 主动沉淀：开发 / 设计 / 排查中产生的信息与决策（运行期约定，非初始化动作）

> **初始化不写任何记忆内容**。本节定义**运行期**口径：AI 在开发 / 设计 / 排查过程中产生的**信息、决策、设计**，必须**由 AI 自己**写入 `${scope}-memory`。
> **硬性口径：用户开口不是触发条件。**「等用户说'记一下'」「收尾时统一补记」都属于本条要禁止的漏写。
> 初始化只把这条约定写进 AGENTS.md（§2.1 ⑩）；写入工具参数、片段格式、归档由 `rules/ai-codekb-memory.md` 负责，本节不重复定义（见 §7）。

#### 一、判定口径（必须现在写，不能攒）

**触发条件是「对话里出现了一条将来还有人要用的结论」，不是「用户要求记录」。**

| 自检 | 结论 |
|---|---|
| 换个会话、换个人接手，这条结论还用得上吗？ | 用得上 → **现在就写** |
| 不写会怎样？ | 下次要重新调研 / 重新问人 / 重新踩一遍坑 → **现在就写** |
| 只是一次性试错、中间状态、随时会被推翻的猜测？ | 不写（等结论稳定；被推翻的旧判断才值得写一句） |

> **不许"先干活，最后统一补记"**：收尾补记在实践中会被截断、被遗忘、被压缩成一句话而丢掉细节。写完一段就落一次。

#### 二、触发 → 落点（按性质归类）

| 对话中出现 | 落点 Group | Relation 命名 |
|---|---|---|
| 技术选型、方案取舍、被推翻的旧判断 | `决策记录` | `{决策主题}` |
| 架构分层、模块职责、依赖方向 | `项目架构` | `{模块名}` |
| 数据流、存储模型、字段口径 | `数据流` | `{链路 / 业务域}` |
| 接口契约、入参返回、错误码 | `接口信息` | `{模块}` |
| 报错根因、踩坑与解法 | `错误库` 或 `项目踩坑点` | `{现象 / 报错关键词}` |
| 某模块怎么用 + 内部实现要点 | `专题记忆/{模块名}` | `{子主题}` |
| 团队约定、提交规范、分支策略 | `团队约定` | `{约定名}` |
| 外部系统、SDK / API 限制 | `外部依赖` | `{依赖名}` |
| 可复用工具函数、脚本要点 | `工具库` | `{分类}` |
| 项目阶段、里程碑、当前状态口径 | `当前状态` | `{阶段}` |
| 以上都不合 | `通用记忆片段/{分类}` | `{分类}` |

> `专题记忆` 组下**必须先建子组**再写 relation（团队约定，系统不校验）。
> 写入路径会自动补建父组，**不必先 `ki_group_create`**。

#### 三、粒度与查重（写坏了比不写更糟）

- **一条 Relation = 一个主题**，正文写「做什么 / 怎么用 / 为什么这么定 / 边界与坑」，不写过程流水账
- **写前必查**：先 `ki_get_module_info` 取回当前正文 —— `ki_sync_relation` 是**整篇覆盖、无追加语义**，直接写第二条会把第一条冲掉；同主题**改**，不同主题才**新建**
- 单条用 `ki_sync_relation`；**≥3 条用 `ki_bulk_sync_relation`**，每批 ≤5 条
- 正文控制在 1000 字符内，超长拆 Relation（超长会被警告且检索质量下降）

#### 四、通道选择：短内容走 MCP，成篇文档走 `ki-upload`

> **沉淀不等于"写 relation"**。正文已在上下文里、只有一段结论 → MCP 工具最快；**已经在本地写好的成篇文档 → 直接上传更省事、检索质量更好**。

| 形态 | 通道 | 理由 |
|---|---|---|
| 一条结论 / 一个主题（几百字 ~ 1000 字符） | `ki_sync_relation`（≥3 条用 `ki_bulk_sync_relation`，每批 ≤5） | 内容已在上下文，直接写最快 |
| **本地已写好的成篇文档**——设计文档、方案、排查报告、调研报告，**内容多的（如 500+ 行）** | `use_skill("ki-upload")` 的 `upload` / `upload-dir` | 自动切分 + 向量化；500 行塞进 relation 必然超长（>1000 字符警告）、检索质量差，还要手工复制粘贴 |

- **怎么选**：一段话能说清、将来只需被检索到一两句 → relation；**有章节结构、需要翻页、达到几百行** → 上传（别因为"上传要装依赖"就改塞 relation，装不上按 §2.4 五 降级给命令）
- **不要"先摘要再写 relation"**：原文直接上传，摘要压缩成「近期工作」一行即可
- **落组必须含 `文档` 段**（如 `专题记忆/{模块名}/文档`、`错误库/文档`），索引才能机械折叠（§2.4 二 / §2.3 折叠条款）
- **上传后验证、缺上传能力时的降级、文件与 ki 同机改走 `ki import`**：与 §2.4 三 / 四 / 五 同一口径，照其执行，本节不复述（避免两套账漂移）

#### 五、写完之后（必做两步，缺一不可）

1. **刷新索引**：AGENTS.md「项目记忆索引」按 `ki_group_list(mode: "full")` 机械转写（§2.3）；写的是「团队约定」组时**同时回刷** AGENTS.md「团队约定」章节（§3.6，空则写"无"）
2. **留一行痕迹**：AGENTS.md「近期工作」记 `- [YYYY-MM-DD] {一句话结论}`（≤ 80 字，详情留在 ki）；**追加后立即数条目数，> 20 条即按 §5 T1 归档**

#### 六、不写什么（边界）

| 不写 | 原因 |
|---|---|
| 用户画像、需求进度 | 只进 AGENTS.md（§3.5），进 ki 会重复且查不到 |
| 一次性调试过程、临时试错、废弃方案过程 | 没有复用价值；结论稳定后的取舍写 `决策记录` |
| 敏感信息（私钥、线上地址、真实 IP、真实账号） | 一律占位符（§8 禁忌 16） |
| `${scope}`（代码知识库） | **默认只读**，需用户明确授权；新知识一律先写 `${scope}-memory` |

> **库名未定 / 未初始化**：目标 scope 以 AGENTS.md 索引章节首行登记为准（§2.0）；项目尚未初始化（无 memory scope）→ 先按 §1.5 引导，**不臆造 scope 名**，也不改写 `${scope}` 代码知识库。

## 3.5 直接存储章节维护（用户画像 + 近期工作）

> **用户画像与近期工作均不再使用 ki scope/Group，直接存储在 AGENTS.md 对应章节。**

### 用户画像

#### 维度（按需新增，不预置空维度）

```
常见维度：沟通偏好 / 工作习惯 / 代码风格 / 工具链 / 技术背景
```

#### 写入规则

- 对话中发现用户偏好 → 直接更新 AGENTS.md 对应小节（覆盖写入）
- 维度缺失 → 新增小节（命名保持 4-8 字名词短语）
- **不硬造内容**：模板只给格式，不预置 6 个空小节的占位文字；没有偏好就只留已观察到的 1-2 个维度
- **只记偏好，不记个人信息**：真实姓名、手机号、邮箱、身份证、住址、公司内部人名一律不写（见 §8 禁忌 16），必要时代称（如"项目负责人"）
- **不执行任何 ki MCP 调用**

#### 读取规则

- 对话开始 → 读取 AGENTS.md"用户画像"章节，加载用户偏好
- 无需任何 ki 查询

### 近期工作

#### 写入规则

- 格式：**单小节、单列表**，每条**严格 1 行**：`- [YYYY-MM-DD] {一句话：做了什么 / 结论是什么}`（≤ 80 字）
- **详情不进 AGENTS.md**：根因、代码位置、验证数据、审查结论 → 写入 `${scope}-memory`（`ki_sync_relation`）或项目 `.plans/` / `.debug/` 台账，AGENTS.md 只留一行结论 + 指向（如 `详见 .debug/xxx/`）
- 状态标记：进行中 `🔄`、已完成 `✅`、待拍板 `🆕`
- **写入前脱敏**：线上域名 / 真实 IP / 账号口令 / Token / 个人信息一律替换为占位符或去掉（如"线上环境"、"`<HOST>`"），见 §8 禁忌 16
- 容量：本章节**目标 ≤ 20 条 / ≤ 40 行**，超过即触发归档（见下）
- **不执行任何 ki MCP 调用**（无"最近需求"/"进度" Group）

> **为什么强制 1 行**：实测某项目该章节 224 条、742 行（占 AGENTS.md 73.5%），而 AGENTS.md 是每次对话全量注入的上下文——流水账详情会把"缓存索引"的成本变成负债。规格与现实的偏差是数量级的，故此处收紧为硬约束。

#### 过期清理（归档）

- 已完成 / 待拍板条目超过 7 天 → 压缩为一行后移入本文件「历史工作记录」章节（按日期倒序追加）
- **进行中 `🔄` 条目永久保留**，不归档
- 归档时保留"结论 + 仍有效的决策"，删除实现细节与验证清单（细节查 git 历史或台账）
- 本文件内归档，**不再创建 `archive.md`**（口径已收敛）

## 3.6 团队约定章节同步（AGENTS.md ↔ ki）

> **同步源**：`${scope}-memory` → 「团队约定」Group。本节是缓存，权威数据在 ki。
> **目的**：agent 读 AGENTS.md 即可直接获取团队约定，免一次 ki 查询。

### 同步规则

- **方向**：先写 ki（`ki_sync_relation(scope: "${scope}-memory", group: "团队约定", relation, module_info)`），再把要点回刷本节。**禁止只在 AGENTS.md 写约定而不写回 ki。**
- **粒度**：每条 Relation 压缩为一行要点 `- {Relation 名}: {一句话要点}`，不全文转储。
- **空值约定**：Group 无 Relation 时，本节内容只写 `- 无`；**禁止留空、禁止删除本节**。
- **刷新时机**：完整初始化（§2.1 ⑤）、增量更新（§2.2 ③）、写入/修改团队约定后。
- **同步日期**：每次回刷时更新本节引用块中的 `同步日期: YYYY-MM-DD`。

### 读取规则

- 对话需遵循团队约定时先读本节；需完整原文再走 `ki_get_module_info(scope: "${scope}-memory", group: "团队约定", relation)`。

## 4. 真实数据 vs 示例数据

> **优先使用 ki 中的真实数据。仅当 ki 中无对应 scope 时，才使用示例格式兜底。**

### 有真实数据时

- 目标 memory scope → 按 §2.0 判定为**唯一一个**（`ki_scope_list` 只用于挑候选，不逐个写入）
- Group 结构 → 来自 `ki_group_list(mode: "full")`（仅该 memory scope）
- 热门 Relation → 来自 `ki_group_list(mode: "hot")`（仅 ${scope}-memory）
- 团队约定 → 来自 `ki_group_list(groups: "团队约定", mode: "full")`，空则写"无"（见 §3.6）
- 主动沉淀 → 来自本 skill §2.5 的**约定文本**（不是 ki 数据；章节内容固定，不随索引变化）
- 知识文档入库 → 来自本 skill §2.4 的**约定文本**（不是 ki 数据；章节内容固定，不随索引变化）
- 近期工作 → AGENTS.md 内已有内容（无 ki 数据源）
- 用户画像 → AGENTS.md 内已有内容（无 ki 数据源）

### 无真实数据时（示例兜底）

在对应章节使用 ⚠️ 标注：

```markdown
## 项目记忆索引

> ⚠️ 项目记忆索引为空，尚未创建任何项目记忆。
> 执行 `ki_group_create(scope: "<memory scope>", path: "背景与目标")` 建首个组（该工具会自动创建不存在的 scope），写入首条 Relation 时其余组自动补建。

## 用户画像

> 用户画像直接存储于本文件。尚无已记录偏好，随对话逐步补充。
```

> 注意：`ki_group_create` 建的是 **Group**，不会创建 scope 之外的任何索引内容；只建组不写 Relation，索引章节仍然是空的。

## 5. 近期工作维护与归档

> **近期工作直接存储于 AGENTS.md，不从 ki 提取；归档也留在本文件（「历史工作记录」章节），不再使用外部 `archive.md`。**
> 本节规则与 `rules/ai-codekb-memory.md`「归档机制」同源，改动须两处同步。

### 写入（格式）

- 单小节单列表，每条一行：`- [YYYY-MM-DD] 🔄|✅|🆕 {一句话结论}`（≤ 80 字）
- 详情（根因 / 文件位置 / 验证数据 / 审查结论）写入 `${scope}-memory` 或项目台账（`.plans/`、`.debug/`），此处只留指向

### 归档触发（任一命中即执行）

| # | 触发条件 | 动作 |
|---|---------|------|
| T1 | **刚往「近期工作」追加了新条目** | 追加后立即数条目数：> 20 条 → **本次就归档**，不留到下次 |
| T2 | 条目日期 > 7 天且状态非 `🔄` | 压缩为一行后移入「历史工作记录」 |
| T3 | 本章节 > 20 条或 > 40 行 | 全量整理一次：按上述规则归档 |
| T4 | 完整初始化 / 增量更新（§2.1 / §2.2） | 顺带检查 T2、T3 |

> **为什么把 T1 放在第一位**：旧规则只有"访问本章节时检查归档"，而"访问"是可跳过的动作——实测某项目因此积累到 224 条 / 742 行，规则形同不存在。**"写入"是必然发生的事件**，把检查点绑到写入后，才不依赖 AI 记得回头自查。
> 配套：`ai-codekb-memory` 规则「会话结束收尾」checklist 同样保留这一项，两处互为兜底。

### 压缩规则

**前置校验（含多行详情时不可跳过）**：条目若带子列表/多行详情，压缩前必须确认详情**已落到** `${scope}-memory`（`ki_sync_relation`）或项目台账（`.plans/`、`.debug/`）；**没落地就先写，再压缩** —— 否则压缩等于删除信息。本来就只有一行的条目直接搬，无需额外落地。

```
保留：结论（做成了什么 / 决定了什么）、仍有效的约束、被推翻的旧判断（一句话）
删除：实现步骤、验证清单、审查过程、失败尝试的中间状态（这些去 git 历史 / 台账查）
```

目标：归档条目每条 ≤ 120 字，按日期倒序追加，不删除历史。

### 存量迁移（首次套用本规则时）

当已存在历史堆积（如数百行、跨数月）时，一次性整理：

1. 按日期分组，`🔄` 的留在「近期工作」
2. 其余逐条压缩为一行，按倒序写入「历史工作记录」
3. 压缩时保留「结论 + 决策」，细节不搬运
4. 整理后在更新日志记一条结构性变更

## 6. 更新日志维护

> **只记结构性变更**，不记日常条目增删（那些在「近期工作」里已有，重复记录会把两处都撑大）。

**记**：新增/删除章节、memory scope 变更、Group 结构大改（一次增删 ≥3 组）、归档整理、模板升级。
**不记**：单条需求追加、单条 Relation 写入、团队约定内容更新。

```markdown
| YYYY-MM-DD | {结构性变更，如"初始化索引缓存"、"归档 2026-09 条目 167 条"、"新增 memory scope: xxx"} |
```

保留最近 10 条，超出删除最早的。

## 7. 协同

- **与 `ai-codekb-memory` 规则**：本 skill 负责 AGENTS.md 的**结构与索引**（用户手动触发）；规则文件负责**运行期行为**（何时写、写哪里、如何归档）。两者共享同一套格式口径，**格式的唯一真源是 `AGENTS-template.md`**，规则与 skill 正文只引用不重定义——历史上两边各写一份「近期工作格式」，结果与真实产物三份互不一致。
  - **「主动沉淀」的分工同理**：**判断层**（什么该沉、落哪个 Group、写后验证、什么不该沉）在 §2.5，且由 AGENTS.md 的「第二原则」章节承载（运行期才看得见）；**执行层**（`ki_sync_relation` / `ki_bulk_sync_relation` 参数、片段格式铁律、批次上限、归档机制）以规则文件为准，本 skill 不复制。
- **与 `ki-search` 规则**：AGENTS.md 索引只缓存 `${scope}-memory`；检索走 `ki-search`，**默认优先 `${scope}-memory`**（`${scope}` 仅作宏观兜底，与 `ki-search` 规则禁忌 10 一致），确认主题在代码库时再查 `${scope}`；两者都确需时才一次传两个 scope（`ki_search(scope: "${scope},${scope}-memory", query)`）。模板顶部须写明这条约定，**不得写成"永远同时查两个 scope"**——那会与 `ki-search` 的"优先 memory"口径打架。
- **与 `ki-upload` skill**：本 skill 定义**判断层**（什么文档该入库、落哪个 Group、怎么验证、怎么回填，见 §2.4）；`ki-upload` 提供**执行层**（`use_skill("ki-upload")` → `upload` / `upload-dir` / `ping` / `status`，含参数、错误码、httpflex 踩坑）。**分工边界**：本 skill 不重写上传参数与错误码，`ki-upload` 不负责 AGENTS.md 结构与 Group 归类。初始化**不触发上传**；缺上传能力时降级为打印命令（§2.4 五），**不阻塞初始化**。**运行期同一条通道也服务主动沉淀**：本地已写好的成篇文档（几百行 / 500+ 行）直接 `use_skill("ki-upload")` 上传，不要塞进 relation（§2.5 四）。
