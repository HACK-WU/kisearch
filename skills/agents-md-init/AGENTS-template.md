# AGENTS.md - AI AGENT 项目记忆文件

## 🔑 第一原则：遇事不决，先取文档（ki_recall → ki_search）

**拿到新任务 / 需求 / bug，第一动作不是搜代码、也不是直接 `ki_search`，而是先取文档：用户提问先 `ki_ask` 拿结论，接到任务先 `ki_recall` 取该读哪几篇，按清单读正文再动手。** 当前会话看不到 `ki_recall`（如只读 Token 会话）时跳过预取、直接用 `ki_search`，并如实说明「本次未预取」。

- **按场景选工具**：**用户提问**（为什么 / 怎么做 / 有没有做过 / 上次怎么定）→ `ki_ask`（先拿库里的既有结论与背景，**再**结合代码回答）；**要动手做任务** → `ki_recall`（该读哪几篇文档）；已知关键词要片段 → `ki_search`
- **顺序**：① `ki_recall`（任务画像 + `scope` 必填）→ 按 `nextActions` 读 ≥1 篇正文 → ② 无候选或需要精确片段时再 `ki_search` → ③ 记忆与代码冲突以代码为准。**不要两套都盲跑一遍**
- **`ki_search` 的库顺序**：先 `ki_search(scope: "${scope}-memory", ...)` 查项目上下文与决策；确认主题在代码库时再查 `${scope}`（代码知识）。**项目已有既定检索口径时以项目为准**，不要按模板强行改写
- **该看视图的两个信号**：① 单库 `ki_search` 结果不足或文不对题；② 问题横跨多域（代码 + 运维 + 专家经验 + 项目决策）。命中时先 `ki_view_list()` 找现成聚合视图；**没有合适视图时**再显式拼多段 scope（`ki_search(scope: "a,b", ...)`，勿长期硬拼）。视图是多个库的**只读**聚合，**视图名可直接当 scope** 传给 `ki_search` / `ki_group_list` / `ki_tag_list` / `ki_get_module_info`。**成员含 `${scope}`、`${scope}-memory` 或 `${scope}-*` 同词根的视图才与本项目相关**，其余忽略；本文件**不缓存视图列表**（会变），每次实时查。同时看 `usableCount / availableCount` 与 `degradedReason` —— 有降级说明时部分成员不参与语义检索。**`threshold` 量级不同**：单库 `0.02~0.03`、视图（多库）`0.6~0.8`，混用会全灭或全留
- **视图只读**：写入（`ki_sync_relation` / 上传文档）必须用真实库名，用视图名会被拒
- 检索口径与工具分工见 `ki-search` skill；预取的画像四要素、返回怎么消费见「第三原则」，判据见 `task-recall` skill

## 📝 第二原则：主动沉淀，不等提示

**开发 / 设计 / 排查过程中产生的信息、决策、设计，AI 自己写进 ki 的 `${scope}-memory`，不等用户说"记录一下"。**

> 用户开口不是触发条件。**真正的触发条件是「这条结论将来还有人要用」**——换个会话、换个人接手还能省掉一次重复调研，就当场写；不写会导致重新调研 / 重新问人 / 重新踩一遍坑，就当场写。
> 不允许"先干活、收尾统一补记"：收尾补记会被截断、被遗忘、被压成一句话而丢掉细节。

- **沉什么、落哪个 Group**：选型与取舍 → `决策记录`；架构分层与模块职责 → `项目架构`；数据流与字段口径 → `数据流`；接口契约与错误码 → `接口信息`；报错根因与解法 → `错误库` / `项目踩坑点`；模块用法与实现要点 → `专题记忆/{模块名}`；团队约定 → `团队约定`；外部依赖限制 → `外部依赖`；可复用工具函数 → `工具库`；项目阶段与当前状态 → `当前状态`；都不合 → `通用记忆片段/{分类}`
- **写前必查重**：`ki_get_module_info` 取回正文 —— `ki_sync_relation` 是**整篇覆盖、无追加语义**，同主题**改**，不同主题才**新建**；单条用 `ki_sync_relation`，**≥3 条用 `ki_bulk_sync_relation`**（每批 ≤5）；单篇正文控制在 **4000 字符**内，超长拆 Relation（超过时返回体带 `warning` 字段，按提示拆条或改走 `ki-upload`）
- **该配图就配图，别只写散文**：调用链 / 数据流 / 分层依赖 / 状态机 / 时序 → 一张 `mermaid` 图；层级与分支 → 文字树；对照 → 表格。**图必须配文字结论**：导入 / 编辑器保存 / 索引重建都会把围栏块整块从向量化输入剥离（MCP 直写不清洗，但图的语法文本占额度、不贡献语义），图只服务"看的人"、不承载检索；**手写 Relation 不放 `![](./x.png)` 真图片**（没有 `assets/` 目录，必然破图），要真图片就写成本地文档走 `ki-upload`
- **写后两步**：① 按 `ki_group_list(mode: "full")` 刷新本文件「项目记忆索引」（写的是「团队约定」组时同时回刷本文件「团队约定」章节）；② 在「近期工作」记一行 `- [YYYY-MM-DD] {一句话}`（≤ 80 字）
- **不写**：用户画像与需求进度（只进本文件）、一次性试错与中间状态、敏感信息（用占位符）、`${scope}` 代码知识库（默认只读，需用户明确授权）
- **发现过时 / 描述错误的文档 → 主动修正或删除，不等提醒**：能改就改（`ki_edit_relation` 改几行 / `ki_sync_relation` 整篇覆盖；本文件的索引、团队约定以 ki 为权威回刷），**确认无用才删**（`ki_delete_relation` 进回收站可恢复，删前先读全文、不删被推翻的旧判断），删除在收尾里写清删了什么、为什么；`${scope}` 代码知识库仍需授权；判据见 `agents-md-init` §2.8
- **库名未定时**：以本文件「项目记忆索引」首行登记的 `${scope}-memory` 为准；项目尚未初始化（无索引章节 / 无 memory scope）→ 先走 `agents-md-init` 引导，**不臆造 scope 名**
- **两条通道（沉淀 ≠ 只写 relation）**：正文已在上下文里的一条结论 → `ki_sync_relation`；**本地已写好的成篇文档（设计文档 / 方案 / 排查报告 / 调研报告，几百行乃至 500+ 行），或需要放真图片 / 多张图 → `use_skill("ki-upload")` 直接上传**，别塞进 relation（>4000 字符会警告、检索质量差，手工复制也易错），也**不必先摘要再写**——原文上传，摘要只留「近期工作」一行；上传落组必须含 `文档` 段（如 `专题记忆/{模块}/文档`、`错误库/文档`），详见「知识文档入库」章节
- **分流：一条结论 vs 一件事**：写完即完的结论 → 走上面的 relation / 上传通道；**要有人推进到收口的事**（bug、技术债、缺失功能、越界发现）→ 事件；本次任务内马上要做的 → 直接做，不建
- **主动上报，不等提醒**：开发 / 设计 / 排查中发现了**不属于当前任务范围**且需要有人跟的事，**当场** `use_skill("event-report")` 上报为事件，并在对话里留一行回执（`📮 已上报 #38「…」`）；**任务收尾再扫一遍**"发现了但没做的事"。等用户说"记一下"同样算漏报
  - 建前查重（`ki_event_list(q, status: "open")`）；命中后**先 `ki_event_get` 读详情确认是否同一件事**（标题相似 ≠ 同一 bug），同一件才挂证据不新建
  - **文档三分法**：**产物文档**（debug 报告 / 需求报告 / 复盘）挂 `docs`（改分类、随阶段），**证据文档**挂 `refs`（零改动）；顺序是**先挂 docs 再推终态**（已收口挂不了）
  - 本次做完的事若对应已有事件 → `ki_event_edit(action=stage)` 推到真实阶段（**已修复不许停在「修复中」**）
  - 判据与操作细节见 `use_skill("event-report")`

## 🔎 第三原则：预取细则（ki_recall）

> 本节是**第一原则第一步**的执行细则：「先取文档、再检索」这个顺序由第一原则定，本节只解决"怎么把预取做对"。

拿到新任务 / 需求 / bug，**动手前先写 2-3 句任务画像并调用 `ki_recall`**（只读、单次、不提问、`scope` 必填）。

- **`scope` 必填**：查哪几个库 / 视图由调用方决定，工具**不会替你挑库**；漏传会报错并回可用清单（含库与视图名）。
- 画像四要素：**目标 / 涉及 / 现象 / 期望**；强线索走 `hints`（错误码、文件路径、函数名、接口名）。
- 拿到候选后按 `nextActions` **读 ≥1 篇正文再动手**。`why` 只说明「靠什么被检索到」（分数 / 库内名次 / 线索词），**不代表读过了** —— **没读过任何一篇正文，不许断言「没有相关文档 / 这些都不相关」**；读不到就说「预取到 N 篇但读不了」。
- `degraded` / `partial` = 结果不完整，要如实说；`skipped` = 那些库没参与（无权 / 不存在 / 超限），不能当成「没有相关文档」。
- 不该预取：闲聊、纯文案、已知位置的一行改动、刚在同一模块做过且结论仍热。
- 与其它工具的分工：预取找文章 → `ki_recall`；已知关键词取片段 → `ki_search`；已知名称读全文 → `ki_get_module_info`；读完了要结论 → `ki_ask`。
- **与「第一原则」的关系**：先后顺序由第一原则定义（预取在最前），本节只管怎么调、怎么读，不重复定义顺序。
- **工具不可见时**：若当前会话看不到 `ki_recall`（例如只读 Token 会话，模型消耗型工具整体不可见），**跳过预取并如实说明**，不要臆造工具调用。

> **能力前提**：本节只在 ki 侧提供 `ki_recall` 工具时写入（由 `agents-md-init` 初始化时探测）。工具不存在时本节不写，避免指导 AI 调用不存在的工具。

## 🧾 第四原则：收尾汇报（做了什么 / 落了什么 / 剩什么 / 等你定什么）

**任务或阶段给出交付结论前，先过一遍 `agents-md-init` skill §2.7 自查（该记没记 / 该报没报 / 该收口没收口 / 该贴的链接没贴），再用一段精炼「收尾」说清四件事，四要素各一行，确实为空就写「无」；写工具返回了 `url` 时再加第 ⑤ 行。**

- **① 状态变更**：事件阶段流转（`📮 #N → 已关闭`）、关键文件 / 端点 / 测试结果、是否已提交
- **② 沉淀落点**：写进哪个库 / Group / Relation，本文件「近期工作」记了哪一行
- **③ 剩余边界**：已知限制、未覆盖测试、待复核项、被推翻的旧判断；**没做的必须写"未做"**
- **④ 待你决定**：需用户拍板的（是否提交、是否 breaking、要不要推到终态）
- **⑤ 文档链接**（条件要素）：本轮用 MCP 写工具（`ki_sync_relation` / `ki_bulk_sync_relation` / `ki_edit_relation`，以及未来任何返回 `url` 的写工具）成功新增或修改了文档、且返回体带 `url` 时，在回复末尾逐条写 `[文档名称](url)`（超 5 篇列前 5 条 + 「共 N 篇」）；**拿不到 `url` 就整条不出现**，绝不自己拼地址；同一链接跨轮次不重复贴
- 只汇报**已经发生**的事（事件真推了、记忆真写了），不写逐文件 diff / 命令输出 / 记忆正文；`📮` 就是回执本身，不重复写第二行；格式真源见该 skill §2.7.1

> **项目专属原则（第五原则及以后）**：本模板只定义 1~4 原则。项目可在第四原则之后追加自己的置顶章节（形如 `## 📦 第五原则：…`，例：某仓把"工具通道选择"固定在这里）。**初始化与刷新时必须原样保留这些模板之外的置顶章节，不得删除或重排**。

## 项目记忆索引

> 数据来源：ki 的 `${scope}-memory` scope（`YYYY-MM-DD` 初始化）。仅缓存此 scope，代码知识库不缓存。
> **转写规则**：下面的 Group 结构与热门 Relation 必须由 `ki_group_list` 输出**逐行机械转写**，禁止读完凭印象重写（会持续漂移）。

### {scope}-memory 索引

#### Group 骨架（按需补建，不必一次建满）

只立即建**必要项**，其余等 `ki_sync_relation` 写入时自动补建（该工具会自动创建路径上缺失的所有节点）：

```text
ki_group_create(scope: "${scope}-memory", path: "团队约定")
# scope 不存在时该工具自动创建并返回 createdScope，无需单独建 scope
```

| Group | 必要性 | 用途 |
|-------|--------|------|
| 团队约定 | **必建** | 「团队约定」章节的同步源（见本文件「团队约定」章节） |
| 背景与目标 / 当前状态 / 项目架构 | 建议 | 高频读写，先有槽位便于归类 |
| 技术栈选型 / 项目历史 / 外部依赖 / 项目踩坑点 / 工具库 / 常用命令 / 部署运维 | 按需 | 首次写入时自动补建 |
| 接口信息 / 数据流 / 决策记录 / 关联关系 | 按需（**高频，建议预留**） | 实测多个项目都会自发演化出这四类 |
| 专题记忆 | 按需 | **必须先建子组再写 Relation**（团队约定，系统不校验） |
| 通用记忆片段 | 兜底 | 无法归入上述分类时用，可再按功能/类型细分子组 |
| 错误库 | 可选 | 踩坑多的项目适用；不需要就别建 |

## 团队约定

> **同步源**：ki `${scope}-memory` → 「团队约定」Group（`ki_group_list(scope: "${scope}-memory", groups: "团队约定", mode: "full")`）。
