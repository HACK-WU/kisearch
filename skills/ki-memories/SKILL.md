# ki-memories 记忆入口

> **一句话**：遇事不决，先翻 ki-memories——有任务描述就用 `ki_recall` 取文档清单，知道关键词就用 `ki_search` 查片段。
> **管什么**：什么时候该查（代码相关性判定）、怎么查（recall 主路径 + search 兜底 + 目录直查）、命中后怎么读（正文必须自己读）、能不能写（默认只读）。
> **不管什么**：定位级查找（grep / SearchSymbol 更快，不走 KB）、命令参数语法（以工具定义为准）。

## 概述

- **目的**：让 agent 动手前先取文档、不凭记忆猜；把「查 / 读 / 写」收敛成一个入口，避免多个记忆 skill 各讲一套。
- **功能**：`ki_recall` 主路径（任务画像 → 候选清单 → 读正文）＋ `ki_search` 兜底四步走 ＋ 目录直查（强关联 / 决策 / 待生效变更）＋ 写入边界（默认只读、白名单、格式与查重）。
- **使用场景**：任何理解级任务开工前；确认既有决策 / 踩坑 / bug 解法；改代码前感知跨模块牵动；发现记忆与代码不符、需要修正时。

## 0. 速览

```
任务 / 问题来了
  ├─ 闲聊、产品方向、会议纪要、一行错别字 → 不介入
  ├─ 定位级（目标明确，一个 grep 能回答）→ grep / SearchSymbol，不走 KB
  └─ 理解级（要架构 / 流程 / 设计意图 / 历史决策 / 踩过的坑）
       ├─ 不知道读哪篇 → ① ki_recall(scope 必填) → ② 按 nextActions 读正文 → ③ 动手
       └─ 知道搜什么词 → §4 四步走

  ki_recall 不可用（未配置模型 / 只读 Token）或无候选 → §4 四步走
  待生效变更（有没有该结账的变更）→ §5 目录直查（它 vector=false，ki_search 查不到）
```

## 0.5 四个工具怎么选

同样是"查知识库"，返回物完全不同，上下文成本差一个量级。**先想清楚要什么，再选工具。**

| 工具 | 返回什么 | 谁做筛选 | 上下文成本 | 限制 |
|------|---------|---------|-----------|------|
| `ki_recall` | **该读哪几篇**的清单（`scope`/`group`/`name`/`why`/`evidence`）+ `summary` + `uncertainties` | ki 侧 LLM 读正文后判断 | 低 | **需要模型**；只给清单不给正文 |
| `ki_search` | **原始命中片段**（`content` + `score`） | 无 LLM，只有 `threshold` 机械过滤 | 高 | 筛选与提炼全在你身上 |
| `ki_ask` | ki 侧模型合成的**一段答案** + 来源 | ki 侧 LLM | 低 | 只接受单个具体库（不吃视图名）；只读 Token 不可用 |
| `ki_get_module_info` | **指定文档全文** | 无 | 中 | 要已知 group + relation |

**选择口诀**：

```
不知道读哪篇，只有任务描述  → ki_recall
知道搜什么词，要原始依据     → ki_search
读完了，要一个综合结论       → ki_ask
知道 group + 名称，要读全文  → ki_get_module_info
```

## 1. Scope 约定

- `${scope}` 未指定时**必须暂停问用户**
- 不确定有哪些 scope → `ki_scope_list()`
- 想跨多个库一起查 → `ki_view_list()` 看有没有现成视图（视图名可直接当 scope 用；**视图只读，不能写入**）
- **`${scope}` 仍是字面量时，禁止执行任何 ki MCP 工具调用**

---

## 2. 主路径：ki_recall

### 2.1 怎么调

```
ki_recall(scope: "${scope}-memory", task: "<任务画像>", hints: ["<错误码/文件路径/符号>"], limit: 8)
```

- **scope 必填**：工具不会替你挑库；漏传会报错并回「可用库 / 视图清单」，按清单补传
- **task 是描述不是提问**：「删除一篇文档后用 ki_search 还能搜到，怀疑向量没删干净」而不是「怎么删向量？」
- **hints 放强线索**：错误码 / 文件路径 / 类名 / 函数名 / 接口名，最多 10 条
- 宽范围检索可传数组 `scope: ["${scope}-memory", "${scope}"]`；**上限 6 个**（超出被截断并记入 `skipped`，reason 为 `truncated`）
- **同一任务只调一次**；`needMore` 说缺哪个维度就补齐后再调一次，**第二次带上 `exclude`**（已读清单，格式 `"scope::group::name"`），避免重复推荐同几篇
- 参数上限：`task` ≤2000 字、`hints` ≤10 条（每条 ≤200 字）、`limit` ≤20

### 2.2 返回怎么消费

| 字段 | 处理 |
|---|---|
| `candidates[]` | **只有 `scope` / `group` / `name` / `why` / `evidence` 五个字段**。按 `why` 命中线索多的先读；`evidence: "full"` = 已读正文，`"snippet"` = 只读到片段，后者支撑的结论要降级 |
| `summary` / `uncertainties` | 整体结论 + 判断不了的点。`uncertainties` 要在回答里保留，不要假装确定 |
| `nextActions` | 已给出可直接执行的 `ki_get_module_info` 参数（`scope` 已是物理库名，不是视图名），照调 |
| `needMore` | 缺哪个维度，补齐后**带 `exclude`** 再调一次 |
| `skipped` | 这些库没参与（无权 / 不存在 / 超限），**不能当成「没有相关文档」** |
| `partial` | 结果不完整（只读到片段或未收口），结论标注「基于有限检索」 |
| `dropped` | 被模型剔除的候选数，仅作信号，不用逐条追 |

### 2.3 三条硬门禁

1. **没读正文不许下结论**：`why` 只说明"是怎么被检索到的"，不代表读过
2. **`skipped` / 0 候选 ≠ 库里没有**：只能说"本次未检索到"，回问用户要线索
3. **记忆与代码冲突以代码为准**，并在结论里注明"记忆已过期"

---

## 3. 读正文（不省的一步）

- 单条：`ki_get_module_info(scope, group, relation)`
- 多条：用 `relations` 数组，**同 group ≤10 条一次提交**（超限报错，按每批 10 条切）；逐条核对 `results`——某条名称写错时**只该项失败、不整体报错**
- `group` 走**模糊匹配** ⇒ 路径从清单**原样复制**，不手打；`relation` 是精确匹配，同样复制
- 读完提炼后回答，**不要全文转储**

---

## 4. 兜底：ki_search 四步走

`ki_recall` 不可用（未配置模型 / 只读 Token / 无候选）时走这条：

```
① ki_search(scope: "${scope}-memory", query, limit: 4, threshold: 0.02, tags: "ki-search")
   ↓ 未命中
② ki_group_list(scope: "${scope}-memory", groups: "目标Group", mode: "hot,emerging")
   → ki_get_module_info 索引取原位
   ↓ 仍未命中
③ ki_search(scope: "${scope}", query, limit: 4, threshold: 0.02, tags: "ki-search")   ← 宏观兜底
   ↓ 仍未命中
④ 回问用户：请提供模块名 / 文件路径 / 功能描述
```

**查询词怎么构造**：`<语义描述> <关键代码符号1> <符号2>`

- 语义描述用自然语言说清要解决的问题（"文档导入断点续传"），别只丢一个词
- 追加类名 / 函数名 / 字段名（`ImportService resumeImport`）：语义管"像不像"，符号管"命中得准"
- `limit: 4` / `threshold: 0.02` 是固定口径；结果不相关先换措辞、换符号重试一次，**不要靠放大 limit 硬捞**

**两条铁律**：

1. `ki_search` **不会替你筛**：过了阈值的低分、跑题、重复条目照样返回，必须逐条读完再判断
2. **不要把 `content` 原文整段转给用户**，也不要把 `threshold` 当相关性担保；要省上下文就改用 `ki_recall` / `ki_ask`

## 5. 目录直查（这三类优先，别用语义检索猜）

强关联、决策记录、待生效变更的条目数量有限、`relation` 名可读，**精确列举比语义召回更全**：

```
① ki_group_list(scope, subtree: "关联关系")            → 列出模块子分组
② ki_group_list(scope, groups: "关联关系/{模块}", mode: "full")  → 列该模块全部条目
③ ki_get_module_info(scope, group, relations: [...])   → 一次取多条
```

- **不要凭代码目录名猜模块名**（代码模块名与 ki 功能模块名常不一致，实测同一模块在 `专题记忆/` 与 `错误库/` 下可能叫不同名字）
- **根分组名以实际列举为准**：规范是 `关联关系` / `决策记录` / `待生效变更`，但历史项目可能把台账放在 `通用记忆片段/待生效变更`；`subtree` 返空时先用 `mode="full"` 看实际根名，**不要直接判"没有"**
- `groups` 必须显式 `mode="full"`：默认 `mode="hot"` 只返最热 5 条且静默兜底，**漏掉的正是冷条目**
- `subtree` 不支持逗号分隔多值，返回头部的提示行要核对实际解析路径
- **待生效变更是强制目录查**：它 `vector=false` 不进向量，`ki_search` 根本查不到

## 6. 写入（默认只读，需用户明确授权）

> `${scope}` **默认只读**。发现记忆与代码不符（架构变更、接口过期、文档过时）需要修正时，**先说清差异 + 取得明确授权**，才可写入。

### 白名单（8 类）

模块职责、API 接口、架构约束、项目通用约定、bug 模式与排查、重构策略、依赖版本约束、测试策略

### 黑名单（6 类）

用户喜好、项目记忆/进度、用户个人信息、一次性诊断、临时偏好、会话短期上下文

### 写入前必做三件事

1. **格式**：纯文本 + `-` 列表；禁 yaml frontmatter、`##` 标题、`|` 表格（会污染向量化）
2. **API**：一律 `ki_sync_relation` / `ki_bulk_sync_relation`（双写 KB + 向量）
   - **禁用 `ki_store` / `ki_bulk_store`**：只写向量层、不写本地 KB，会产出孤儿向量
   - `vector=false` ⇒ 只写 KB 不生成向量，**仅待生效变更使用**（台账是待办不是知识，进向量会污染召回）；它**不等于不入库**
3. **查重**：先 `ki_group_list(groups, mode="full")` 列出同 group 既有条目 → **有同 relation 则更新，不新建**
   - 批量写入时整个 group **只查一次**，不要每条各查
   - 错误库的 `relation` 是"错误特征"，同一报错换路径也算同一条

### 写入方式

| 条数 | 方式 |
|------|------|
| 1~2 | `ki_sync_relation(scope, group, relation, module_info)` |
| ≥3 | `ki_bulk_sync_relation(scope, items)`，**每批 ≤5 条**（`items` 硬上限 50） |
| 已有长文档只改几行 | `ki_edit_relation`（`edit` → `view` 轮询 → `finish`），不要整篇重写 |

写入后**必须刷新**（`ki_group_list(mode="full")`），否则低频写入的记忆可能检索不到。`vector=false` 的条目用目录直查校验，**不可用 `ki_search` 校验**。

### 删除

`ki_delete_relation` **仅用于待生效变更结账**（先落地正式变更并确认落盘，再删台账）；其余类型靠覆盖更新，删除会丢失历史。

## 7. 记忆落在哪

| 类型 | group | tags | 向量 |
|---|---|---|---|
| 专题记忆 | `专题记忆/{模块}` | — | 是 |
| 接口信息 | `接口信息/{模块}` | `api` | 是 |
| 数据流 | `数据流/{模块}` | `data` | 是 |
| 决策记录 | `决策记录/{模块}` | `decision` | 是 |
| 错误库 | `错误库/{模块}` | `error` | 是 |
| 强关联 | `关联关系/{模块}` | `relation` | 是 |
| 待生效变更 | `待生效变更/{模块}` | `pending` | **否**（`vector=false`） |

> 子目录七类统一按**功能模块名**；技术栈 / 工具名写进正文与 keywords，不占 group 位。无明确归属模块的（Docker / Nginx / 工具链 / 语言级问题）归 `错误库/通用`、`待生效变更/通用`。
>
> **写入按规范根名，读取按实际根名**：新建条目用上表的根分组；查存量时若 `待生效变更/` 返空，先看 `通用记忆片段/待生效变更`（早期写法遗留）。

## 8. 禁忌清单

| # | 红线 |
|---|---|
| 🔴 1 | `${scope}` 仍是字面量时执行任何 ki MCP 调用 |
| 🔴 2 | 拿到 `ki_recall` 候选**不读正文**就下结论 |
| 🔴 3 | 把 `skipped` / 0 候选说成"知识库里没有" |
| 🔴 4 | 未经用户明确授权修改 `${scope}` 知识库 |
| 🔴 5 | 用 `ki_store` / `ki_bulk_store` 写知识（孤儿向量） |
| 🔴 6 | 把用户喜好 / 项目进度 / 临时上下文写进 ki |
| 🔴 7 | 同一任务连续调 `ki_recall` ≥3 次（该修任务画像，不是重试） |
| 🔴 8 | `ki_search` 未按 `limit: 4, threshold: 0.02` 执行，或靠放大 `limit` 硬捞 |
| 🔴 9 | 把 `ki_search` 的 `content` 原文整段转给用户 |
| 🔴 10 | 优先查 `${scope}` 而非 `${scope}-memory`（`${scope}` 仅作宏观兜底） |
| 🔴 11 | 用 `ki_search` 校验 `vector=false` 的条目（它不进向量，必然查不到） |

**写前自检**：scope 解析了吗？是项目代码知识吗？走对通道了吗？获用户授权了吗？
