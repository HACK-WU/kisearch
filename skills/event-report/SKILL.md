# event-report 事件上报与收口

## 概述

**目的**：解决"AI 在做任务时发现了越界的事（bug、技术债、缺失功能），但不主动上报，要等用户提醒"的漏报问题；同时守住两个事故面——**同一件事重复建事件**、**文档与事件的归属关系挂错**（产物挂成引用、或把被引用的知识改成了事件文档）。

**功能**：
- 三档分流：结论进记忆 / 事情进事件 / 本次就做的不建
- 三道上报门 + 两个必然触发点（越界即报、收尾强扫）
- 固定字段模板（title / type / stage / description 首行来源行）
- 建前查重（`ki_event_list`），命中则挂证据不新建
- **文档三分法**（§5）：产物挂 `docs`（改分类、随阶段）、证据挂 `refs`（不改属性）、独立知识不挂
- 读详情（`ki_event_get`）：结论全文 / 未确认点 / 已确认位置 / 引用；`ki_event_list` 只有 120 字预览，**判断"解决了没有"必须用 get**
- 收口（`ki_event_set_stage`）与召回（接手模块先查未收口）
- 降级：只读会话 / 无 scope / 无权限 / 类型重名 / 敏感信息
- 每次上报必有一行对话回执

**使用场景**：
- 开发 / 设计 / 排查中发现了不属于本次范围的问题（bug、技术债、文档过期）
- 任务做完，回看过程中"应该有人跟"的事没做
- 用户说"这个记一下"、"上报一下"、"别等我提醒"
- 接手某模块，想知道有哪些未收口事件在跟
- 不适用：只是写一条结论 / 知识（走 `use_skill("ki-search")` 的 MCP 写入）；多步骤任务的执行台账（走 `plan-track`）；把文档绑到已存在的事件上（`use_skill("ki-upload")` 的 `--event`）

## 0. 速览

```
一条发现
  ├─ 要不要有人推进到"做完"?
  │    ├─ 否 → 结论/知识 → ki_sync_relation（不进本 skill）
  │    └─ 是 → 是否属于当前任务范围?
  │            ├─ 是 → 本次就做，不建
  │            └─ 否 → 已有未收口事件在跟?
  │                    ├─ 有 → 补挂文档（产物→docs / 证据→refs，§5）+ 回执指 #id
  │                    └─ 无 → ki_event_create（docs? 产物 / refs? 证据，§5）
  └─ 例外：单点风格/命名、需用户先拍板的事 → 不建，对话说一句

收尾必做：本次做完的事若对应某事件 → ki_event_set_stage 推到当前真实阶段
```

## 1. 判据：一条发现该去哪（唯一真源）

| 发现的性质 | 去哪 | 判据 |
|---|---|---|
| 结论 / 知识，写完即完 | `${scope}-memory` 的 relation | 没有"做完"这个状态 |
| **一件事**，要有人推进到收口 | `ki_event_create` | 有阶段、会挂起来等人做 |
| 本次任务内马上要做的 | 直接做，不建 | 做完就消失 |
| 单点风格 / 命名 / 措辞 | 对话说一句，或顺手改 | 不值得留档 |

**一句话判据**：*这条发现要不要有人动手推进到某个终点？* 要 → 事件；不要但有复用价值 → 记忆；都没有 → 不记。

> 本表是判据的**唯一真源**。`AGENTS.md` 与记忆规则只保留一句指针，不复制本表。

## 2. 三道上报门（全过才建）

| # | 门 | 不通过时 |
|---|---|---|
| 1 | **不在当前任务范围内**（越界） | 属本次范围 → 直接做 |
| 2 | **需要有人推进到收口**（有终态、会挂起来） | 只是知识 → 写记忆 |
| 3 | **无同事项**：先 `ki_event_list(scope, q: "<标题关键词>", status: "open", limit: 10)` 找同题，命中后再 `ki_event_get(event: "#N")` **读详情确认是不是同一件事** | 标题相似 ≠ 同一问题（#36「删除后向量残留」与 #37「hidden 仍可召回」标题高度重叠，是两起不同 bug）→ 同一件走 §6 追加；不同件正常新建，描述里注明「与 #N 相关但不同事」 |

## 3. 两个必然触发点

| 时机 | 动作 | 为什么 |
|---|---|---|
| **越界即报** | 一发现且三道门全过 → 当场建，不等任务结束 | 收尾补记会被截断、遗忘、压成一句话而丢细节 |
| **任务收尾强扫** | 结束前扫一遍"我发现了但没做的事"，逐条过三道门 | 把检查绑在"收尾"这个必然发生的事件上，才不依赖"记得" |

> **不要**设"随时想报就报"的松散入口——那等于没有入口。

## 4. 建事件：操作序列

```
① ki_event_type_list(scope)            # 首次用 / 不确定类型时；拿阶段链与 terminalAction
② ki_event_list(scope, q: 关键词, status: "open", limit: 10)   # 找同题（门 3）
③ ② 命中 → ki_event_get(event: "#N") 读详情，确认是不是同一件事
     ├─ 同一件 → 补挂文档：产物 ki_event_docs / 证据 ki_event_refs（§5）   # 结束，不新建
     └─ 不同件 → 走 ④（description 里注明「与 #N 相关但不同事」）
   ② 未命中 → 走 ④
④ ki_event_create(scope, title, type, description, docs?, refs?)   # 产物→docs，证据→refs（§5）
⑤ 回执一行（§10）
```

### 字段模板

| 字段 | 怎么填 | 注意 |
|---|---|---|
| `scope` | 走**项目记忆库**（AGENTS.md「项目记忆索引」首行登记的 `<scope>-memory`）；未登记 → 问用户一次，不猜 | 事件按 scope 隔离，建错库等于没人看得见 |
| `title` | `{模块/对象} {现象}`，**≤ 40 字**，必须含检索锚点（模块名 / 报错关键词） | 去重靠 `q` 模糊匹配标题，标题没锚点就去不了重 |
| `type` | bug → `bug 排查`；慢 / 内存 / CPU → `性能优化`；缺失功能 / 改造 → `需求实现`；都不像 → 用最接近的，并在描述首行写 `分类：<自定义说法>` | **类型建后不可改**（无改类型工具），只能删了重建 → 不确定先问一句 |
| `stage` | **不传**（缺省首阶段） | 从中间阶段起步会让文档可见性提前放开；阶段可从首阶段逐步推进，类型不能 |
| `description` | 三段固定模板（见下），≤ 4000 字 | 会注入事件 AI 分析的上下文 |
| `docs` | 只传**产物文档**（这次任务产出的 debug 报告 / 需求报告 / 复盘 / 验收等，`group` + `name`）；没有就留空 | 会把文档分类改成 `event`、可见性随阶段；挂前按 §5 看 `terminalAction` 与数据源锁 |
| `refs` | 只在**已有**证据文档时传（`group` + `name`，各 ≤50）；没有就留空 | 不要为了填 refs 现造文档；证据与产物是两种东西（§5） |

`description` 三段模板：

```text
来源：AI 自主上报 · {当前任务一句话}
现象：{什么情况下出现什么，含 file:line / 命令 / 报错原文}
为何不在本次做：{一句话}
```

## 5. 文档三分法：产物挂 `docs`，证据挂 `refs`

两个工具做的是**不同的事**，不是「一个安全一个危险」：

| 工具 | 语义 | 对文档做了什么 | 典型文档 |
|---|---|---|---|
| `ki_event_docs` | **归属**：这份文档是这件事的产物 | 分类改成 `event`，可见性随阶段走 | debug 报告 / 需求报告 / 设计 / 复盘 / 验收报告 |
| `ki_event_refs` | **引用**：这件事用得上这份已有知识 | 零改动，保持原分类与原档位 | 库里既有的背景文档、外部依据 |

判据一句话：**「这件事收口之后，这份文档还有独立存在的意义吗？」** 没有 → 它是产物，挂 `docs`；有 → 它是引用，挂 `refs`。

### 挂 `docs` 前必须知道的四件事

1. **可见性由阶段决定**：`hidden` = 语义与全文都搜不到（仍可按 `group`+`name` 精确读）、`fts-only` = 只能全文搜到、`full` = 都能搜到。工具返回的 `hint` 会说明当前档位，**必须转告用户**，不能只说"已关联"。
2. **收口动作决定终局**：先 `ki_event_type_list` 看 `terminalAction` —— `keep` 在收口时把文档转回长期保留（继续可检索），`trash` 会把文档**送进回收站**（如「性能优化」）。后者挂之前要跟用户确认一句。
3. **顺序铁律：先挂文档，再推终态**。已收口的事件挂不了文档（`EVENT_CLOSED`），所以「推到终态之后再补挂产物」这条路走不通。
   产物晚于收口才写完时（复盘报告常见），两条出路：让用户**在页面重新打开**该事件 → 挂 docs → 再推终态；或退一步挂 `refs`（不改分类，但不随阶段流转）。
4. **数据源文档挂不了**：`isImported=true` 的文档分类固定为长期保留，改分类会被拒（`DATASOURCE_LIFECYCLE_LOCKED`）；这类文档只能走 `refs`。

### 同一篇不能既 `docs` 又 `refs`

`ki_event_refs` 会拒与关联文档冲突的项（`REF_ALREADY_ASSOCIATED`）。要升级（refs → docs）就先 `ki_event_refs(action="remove")`，再 `ki_event_docs(action="add")`。

### 成篇的产物文档走 `ki-upload`

产物文档通常几百行，不要塞进 `ki_sync_relation`：用 `use_skill("ki-upload")` 的
`upload <文件> --scope <库> --group <组> --lifecycle event --event '#N'`。它会在上传前自动查一次事件状态（存在性 / 是否收口 / 阶段），返回里带 `event` 字段。

## 6. 去重与追加（第二次遇到同一件事）

```
已有未收口事件（先用 ki_event_get 确认是不是同一件事，别只看标题）
  ├─ 有产物文档    → ki_event_docs(action="add", event="#N", docs: [...])   # 改分类、随阶段（§5）
  ├─ 有引用文档    → ki_event_refs(action="add", event="#N", docs: [...])   # 零改动（§5）
  ├─ 阶段已推进    → ki_event_set_stage(event="#N", stage: "<下一阶段>", note: "<一句依据>")   # 推进一步，不跳阶
  └─ 发现判断错了  → 不要静默删；告知用户后按需 ki_event_delete（须事件已收口）
回执：📮 已在 #37 跟踪，已补 1 篇证据
```

## 7. 收口（别让事件停在中间阶段）

**触发**：本次任务的工作对象就是某个事件（用户说"修一下 #36"，或事件标题与本次任务同指）。

| 完成后实际情况 | 动作 |
|---|---|
| 只定位到根因，未修 | 推到「已定位」 |
| 已修完，未验证 | 推到「修复中」/ 对应阶段 |
| 已修完且验证通过 | **先把产物文档挂成 `docs`（§5），再推到终态** —— 顺序不能反：已收口的事件挂不了文档。推终态前先看 `terminalAction`（`trash` 会把文档送进回收站） |
| 已收口但还需返工 | `EVENT_CLOSED` 会被拒 → 告知用户"需在页面重新打开"，不重试 |

**硬判据**：不要让"已修复"和"修复中"同时存在。事件页停在中间阶段 = 这个闭环断了，下次没人知道它到底做完没有。

**推终态前先读一遍未确认点**：`ki_event_get(event: "#N")` 的 `analysis.unconfirmed` 若还有没核实的项，先核实、或在 `note` 里写清"已知未核实原因"再推。把"待确认"当"已完成"推上去，等于给下一个人留了个假象——他看到的会是"已关闭"，而里面还躺着 4 个未回答的问题。

> 推到终态不可逆（MCP 无重新打开工具，只能在页面操作），所以**终态慎推**。

## 8. 召回（入）

动手改某模块前，一次查询即可：

```
ki_event_list(scope, q: "<模块名>", status: "open", limit: 10)
```

- 有命中 → 先 `ki_event_get(event: "#N")` 读详情（结论全文 / 未确认点 / 已确认位置 / 参考文档 / 阶段日志）再动手；避免重复上报；对话里给一行"另有 N 条未收口事件与本模块相关：#31、#35"
- 无命中 → 不追问、不刷屏
- **不做**全量扫描（成本高且无关），只在"要动这个模块"时查
- **结果可能不可信**：事件池里可能有测试 / 试验事件（标题带日期前缀、描述一两句、长期停在首阶段）。召回只用来「避免重复上报」，**不当作工作状态依据**——与本次任务无实质关联的标题直接忽略，不追着读、不在对话里罗列、不据此推断"这块还有问题"

## 9. 降级（一律不阻塞当前任务）

| 情形 | 表现 | 处置 |
|---|---|---|
| 只读会话 / 无 `knowledge.write` | 写工具在 `tools/list` 里根本不存在 | 不重试、不换工具绕；对话里列出"本应上报的项"，说明无法写入 |
| scope 未初始化 | 查询报 scope 不存在 | 不猜 scope 名、不建到别的库；提示跑 `agents-md-init`；本次只在 AGENTS.md「近期工作」留一行 |
| 类型重名 / 不存在 | `TYPE_NOT_FOUND` + `available` 列表 | **改传 id**（`et_1`），不猜名称 |
| 描述超长 | `EVENT_DESCRIPTION_TOO_LONG` | 压到 4000 内，保住来源行与现象 |
| 阶段不存在 / 已停用 / 与当前相同 | `STAGE_NOT_FOUND` / `STAGE_DISABLED` / `STAGE_UNCHANGED` | 用 `ki_event_type_list` 取真实阶段名；相同则不动 |
| 事件已收口 | `EVENT_CLOSED` | 停手，告知需页面重新打开 |
| 敏感信息（私钥、真实地址、账号） | — | 脱敏后再写（描述会进 AI 分析上下文） |

## 10. 回执（没有回执 = 视为未上报）

每次上报 / 追加 / 流转，对话里必须出现一行：

```
📮 已上报 #38「hidden 文档仍可被语义召回」（bug 排查 · 排查中）
📮 已在 #37 跟踪，已补 1 篇证据
📮 已流转 #36 → 已关闭
📮 无法上报（只读会话）：本应上报 2 项 —— ① … ② …
```

**禁止静默写库**：用户看不到的上报，等于给事件页制造噪音。

## 11. 反模式

- ❌ **把结论也建事件**（"这个库不支持并发写" 属记忆，不属事件）
- ❌ **代码风格 / 命名 / 措辞建事件**（噪音的主力来源）
- ❌ **建前不查重**（同标题满屏，事件页失去可读性）
- ❌ **把 `conclusionPreview` 当结论**（list 只给 120 字预览；判断"解决了没有"、要不要收口，必须 `ki_event_get` 读全文与未确认点）
- ❌ **只看标题就把新发现挂到旧事件上**（#36 与 #37 标题高度重叠却是两起 bug；必须先 get 读描述与结论再判同一件事）
- ❌ **把证据文档挂成 `docs`**（改掉它的分类与可见性，库里凭空少一篇可检索知识）—— 产物才挂 `docs`，见 §5
- ❌ **推到终态之后才补挂产物文档**（`EVENT_CLOSED`，必然失败）
- ❌ **直接从中间阶段起步**（可见性提前放开，且回退要再动一次）
- ❌ **推到终态前不问用户**（`trash` 类型会把文档送进回收站）
- ❌ **上报后跑去调研该问题**（越界发现只登记，不接管；当前任务继续）
- ❌ **静默写库**、或只在收尾时飘一句"顺手记了一下"
- ❌ **已修复不流转**（事件页失真，等于没闭环）
- ❌ **类型拿不准就建**（类型不可改，只能删了重建）
- ❌ **等用户说"记一下"才上报**

## 12. 首次使用自检

1. **AGENTS.md 有上报触发行吗？** 搜 `use_skill("event-report")`。缺 → 提示用户一次："建议把上报触发写进 AGENTS.md 第二原则（做法见 `agents-md-init` §2.1 ⑩）"，然后**照常执行本次上报**，不阻塞。
2. **`ki_event_type_list` 可用吗？** 不可用 → 只做记忆通道 + 回执说明，不卡住任务。
3. **目标 scope 明确吗？** 不明确 → 问一次，不猜。
4. **事件池可信吗？** 大量未收口事件停在首阶段、标题像测试数据 → 只做「建新事件」，不主动召回、不依据存量判断工作状态（见 §8 末条）。

## 13. 协同

| 对象 | 关系 |
|---|---|
| `agents-md-init` | 它负责把**触发约定**写进 AGENTS.md（第二原则）与模板；本 skill 负责**执行**。判据真源在本 skill §1，AGENTS.md 只留指针 |
| `agents-md-init` skill（记忆口径） | 分流表里"结论 / 知识"分支由它执行（`ki_sync_relation` / `ki-upload`，见其 §2.5 / §2.6）；本 skill 只管"一件事"分支 |
| `ki-upload` | **成篇的产物文档走它**：`upload --lifecycle event --event '#N'`，上传前会自动查事件状态（存在 / 收口 / 阶段）。它绑定的是 `docs`（归属），不是 `refs`（引用）—— 选哪个看 §5 |
| `code-review` / `debug` / `design-craft` / `auto-review` | 它们的收尾出口检测到越界发现时，调 `use_skill("event-report")` 继续；不复制判据 |
| `ki_event_list` / `ki_event_get` | **list 用来找**（模糊 + 摘要），**get 用来读**（全文 + 按需裁剪）；判断结论 / 未确认点一律用 get |
| `plan-track` | 台账记"这件事怎么做"；事件记"这件事有没有收口"。互不替代 |
| `ki-search` | 上报前若不确定是否已有相关事件 / 相关文档，先查 |

| 🔴 5 | 从中间阶段起步建事件 |
