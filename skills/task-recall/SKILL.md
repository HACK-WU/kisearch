# 开工前预取（task-recall）

> **一句话**：不知道读哪篇时，先给 `ki_recall` 一段任务画像，它回你一份「该读哪些文档 + 建议阅读顺序」。

## 为什么要预取：先建立记忆基线

任务开工前最贵的错误通常不是写错代码，而是**跑偏**和**遗漏**：

- **跑偏** —— 不知道这里已有决策、曾被否决，按旧结论做完再返工；
- **遗漏** —— 不知道同模块踩过坑、接口有契约，改完才发现动了别人的边界。

`ki_recall` 就是把这两类材料**在动手前**摆出来：既有决策 / 同模块实现记录 / 错误库 / 接口契约。
它的产出不是"资料列表"，而是一份可执行的**记忆基线**：先读哪几篇 + 整体结论 + 判断不了的点。

> **同一套检索逻辑也在「AI 查找」里跑**（事件详情 → 给参考文档）：动作完全一样
> （提线索 → 检索 → 读正文核对 → 判定 → 取舍），差别只在**落点** ——
> 那边产物是候选、由人勾选后写入参考文档；这边是清单、由 agent 直接消费。

## 0. 速览

```
新任务?
  ├─ 不预取 → 闲聊 / 纯文案 / 已知位置的一行改动 / 刚在同一模块做过且记忆仍在
  └─ 预取   → ① 定 scope（必填）→ ② 写任务画像（2-3 句）
              → ③ ki_recall → ④ 按 nextActions 读前 1-2 篇 → ⑤ 再动手
```

> **硬门禁（不满足不许往下走）**：`ki_recall` 只告诉你「文档是**怎么被检索到的**」（分数、库内名次、线索词），
> **不代表它读过了、确实相关**。所以 —— **没读过 `nextActions` 里任何一篇正文，不许在结论里写
> 「知识库里没有相关文档」或「这些都不相关」，也不许据此判断某模块"没有约定/没有先例"。**
> 读不到（文档不存在 / 无权）时，如实说「预取到了 X 篇但读不了」，不拿它当"没有"。

- **`scope` 必填**：查哪几个库 / 视图由你决定，工具**不会**替你挑库，漏传会直接报错并回可用清单。
  - 本项目的默认范围由 **AGENTS.md / 团队约定**给出（如某项目约定「项目记忆 + 专家资产」用一个视图打包）；照它传即可。
  - 不知道有哪些库 / 视图就先 `ki_scope_list` / `ki_view_list`；同一 scope 反复传说明该收敛成视图（由管理员建）。
- 只调**一次**；`needMore` 补完线索后可再调一次，仍不够就转而用 `ki_search`。

## 1. 什么时候预取

| 该预取 | 不该预取 |
|---|---|
| 不熟悉该模块 / 第一次碰 | 一句话改错别字、纯样式取值 |
| 需求或 bug 只有现象、没定位 | 明确知道文件与行号 |
| 改动会跨 3 个以上文件 | 刚在同一模块做过、结论还热 |
| 上次的结论可能已过期（超过两周） | 纯机械迁移（重命名 / 挪目录） |

## 2. 怎么写任务画像（是「描述」，不是「提问」）

四要素，2-3 句，≤2000 字：

```
目标：要达成什么（一句话）
涉及：哪个模块 / 页面 / 接口 / 文件（知道多少写多少）
现象：报错原文、错误码、复现路径（bug 类必填）
期望：改成什么样 / 验收标准
```

- ❌ 不要写成问题句（「这个怎么改？」）—— `ki_recall` 不回答问题，只找文档。
- ❌ 不要贴整段日志或代码 —— 用 `hints` 传强线索（错误码 / 文件路径 / 函数名 / 接口名），最多 10 条。
- ✅ 已有线索（如 `delete-relation`、`422`、`src/lib/x.ts`）一股脑塞进 `hints`，它们最管用。

## 3. 怎么用返回

| 字段 | 怎么处理 |
|---|---|
| `candidates` | 先读 `rankInScope` 靠前、`why` 里命中线索最多的。`score` 是**库内**相对分位，跨库不能横比 |
| `alsoIn` | 这条候选在别的库还有同名文档 ⇒ 两个版本可能不一致，**先读一个、必要时对照**，不要假设等价 |
| `nextActions` | 已经给出可直接执行的 `ki_get_module_info` 参数，照调即可（`scope` 是物理库，别改成视图名） |
| `needMore` | 说明画像缺哪个维度（现象 / 错误码 / 模块）—— 补齐后**最多再调一次**，不要反复重试 |
| `skipped` | 这些库没参与（无权 / 不存在 / 超出上限），**别当成「没有相关文档」**，必要时告诉用户 |
| `degraded` / `partial` | 结果不完整，结论里要如实标注「基于有限检索」 |
| `excludedHidden` / `dropped` | 有内容被剔除（不可见 / 已读 / 索引已不存在），候选少不代表库里没有 |

## 4. 禁忌

| # | 红线 |
|---|---|
| 🔴 1 | 把 `ki_recall` 当问答（它不是 `ki_ask`，不产出结论） |
| 🔴 2 | 同一任务连续调用 ≥3 次（说明画像或 scope 有问题，先修画像） |
| 🔴 3 | 拿到候选**不读正文**就下结论 |
| 🔴 4 | 把 `needMore` 当成向用户反问的借口 —— 先自己补线索 |
| 🔴 5 | 用 `ki_recall` 替代 `ki_search` 做精确关键词检索 |
| 🔴 6 | 漏传 `scope`（报错会回可用清单，照着补一次即可，不要盲试库名） |
| 🔴 7 | **没读过正文就断言「没有相关文档 / 这些都不相关」**（`why` 只说明怎么被检索到的） |

## 5. 与其他工具的分工

```
ki_recall          → 我只有一段任务描述，不知道读哪篇   ← 开工第一步
ki_search          → 我知道搜什么词（或 recall 无候选时）
ki_get_module_info → 我知道 group + 名称，要读全文
ki_ask             → 我读完了，要一个综合结论
```

- **顺序**：先 `ki_recall`；**无候选**或需要精确片段时才 `ki_search` —— 不要两套都盲跑（白花一次往返）。
- **看不到 `ki_recall` 时**（例如只读 Token 会话，模型消耗型工具整体不可见）：**跳过预取并说明**，不要臆造工具调用，直接按已知信息开工或降级用 `ki_search`。

> 预取结果与代码实际不符时：**以代码为准**（与 `ki-search` 同一条规则），并在结论里说明差异。
